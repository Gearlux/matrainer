# Matrainer Mandates

## Current state

An experiment-**tracking** library PLUS, since 2026-08-06, the workspace's **shared trainer machinery** (see the "Trainer API" mandate below — a user-authorized reversal of the old tracking-only rule), with a light core install: `matrainer.tracking` (the `Tracker` ABC + lazily-importing backends, provenance, system metrics), `matrainer.runnable` (the abstract `TrainerRunnable` API base), the per-framework subpackages `matrainer.lightning` / `.fastai` / `.keras` / `.tensorflow` / `.huggingface` (tracking helpers + the framework's runnable bases: since P5 `.keras` carries the FAMILY base `KerasTrainerRunnable` + the compile/fit machinery `KerasRunnable`, and `.tensorflow` the native-loop machinery `TensorFlowRunnable`; since P6 `.huggingface` carries the `transformers.Trainer` machinery `HuggingFaceRunnable`, `.jax` the jitted optax loop `JaxLoopRunnable`, and `.mlx` the MLX loop `MlxLoopRunnable`), plus `matrainer.checkpoints`, `.run_names`, `.sweep` (the tracker-side halves of a backend sweep — naming its experiment and reading it back; lifted from three byte-identical example scripts 2026-08-06), `matrainer._exports` (the PEP-562 lazy-name machinery the task projects' package roots run on), `matrainer.cli` (the trainer-CLI FACTORY the task projects' `cli.py` modules and the `matrainer` console script are built from — see its mandate), and `matrainer.torch` (`load_lightning_checkpoint` + the Lightning-free metric helpers + `MetricsSpec`/`write_collection_sidecar` + the torch family/machinery bases `TorchTrainerRunnable`/`TorchLoopRunnable`). Still: **no data plumbing** — runs go through `recordstream run`, the per-project CLIs, or the generic `matrainer` binary; the runnable protocol, workflow combinators and `DatasetProcessor` live in recordstream, and so do the dataset normalizer, the prediction contracts, the predictions sink, the batch read-back and the loader slots. Data is the recordstream **record** (a plain dict of typed values); matrainer never reshapes it.

**The name (renamed from `marainer` 2026-08-03):** *matrainer* = **mariner** (the one who keeps the log — every heading, every reading, every condition of the voyage) + **trainer** (the thing being logged). It is a mnemonic for the invariant above, not decoration: a mariner writes the ship's log, they do not steer — which is exactly why there is no training loop here, and why the run manifest is the UNION of everything known about a run rather than whatever the current backend has a slot for. Old spellings (`marainer`, `Marainer`, `MARAINER`, the `marainer-*` entry-point names, `MARAINER_TEST_*` env vars, `Gearlux/marainer`) are GONE with no back-compat alias — a stale `import marainer` fails loudly, which is the intent.

- **A SWEEP's Tracker-Side Halves Live Here; Its MATRIX Does Not (`matrainer.sweep`, 2026-08-06):** a sweep runs ONE config under every backend a task project has, into one tracker, and it has two halves that are queries against a TRACKER rather than anything a task knows about: naming this run of it (`<prefix>_<N>`, N one past the highest ALREADY RECORDED — counted from the tracker, so a wiped tracker restarts at 1 where a local counter file would keep counting a history that is gone) and reading it back (`collect` + `render`). Both moved here at the THIRD consumer, which is the trigger the workspace root `TASKS.md` recorded at the second — and the evidence was decisive: the two existing `examples/sweep/sweep_report.py` copies were **byte-identical under an AST comparison with docstrings stripped**, differing only in line wrapping and which metric names their comments cited. It belongs to matrainer by the same argument that moved `metric_slots` and `metric_names`: the thing being queried is a `Tracker`, and the vocabulary the report FOLDS on (`epoch`/`runtime`/`samples_per_second`/`total_flos`, plus Lightning's within-epoch `_step` suffix) is `metric_names`' own. **The DRIVER joined the tracker-side halves on 2026-08-07 (user decision):** `matrainer.sweep` is now a PACKAGE — `report.py` (the original module, verbatim), `spec.py` (the declarative sweep SPEC a project ships as `examples/sweep/sweep.yaml`: its frameworks with `requires` find_spec probes / per-row `env` pins / model variants, its trackers, `tracker_setup` commands, an optional `command:` override) and `runner.py` (the machinery lifted from three near-identical per-project bash drivers: probe INSTALLED not declared, ONE subprocess per cell — Keras binds one engine per process — per-row env scoped to its one subprocess, failure ISOLATED with the report rendered BEFORE the non-zero exit). Three modes: `backends` (frameworks × models, one tracker), `trackers` (every tracker, one framework), `all` (the product) — each tracker gets its OWN experiment from the same date-prefix counter. The default per-cell command is the generic `matrainer train <config> --framework F --tracker T --experiment_name E --run_name R` (invoked as `python -m matrainer.console`, so PATH does not matter). **What must NOT follow it is the task project's half** — `all_backends.yaml` and `sweep.yaml` carry the matrix, the per-engine quirks and the metric alignment, which are exactly what differs between tasks; do not grow this package a notion of what a backend or a task IS (the spec's `env`/`requires`/`tracker_setup` are where a project states its quirks). **Three shape rules:** (1) the command surface is the `matrainer` console script's `sweep` group AND the module main (`python -m matrainer.sweep`) — the SAME `main`, and the report commands' pinned exit-code surface is unchanged; (2) the two former module constants are PARAMETERS (`save_dir=DEFAULT_SWEEP_LOGS`, `tracking_uri=DEFAULT_MLFLOW_URI`) — a hardcoded `./sweep_logs` is fine in an example script and wrong in a library; (3) `QUERYABLE` is LOAD-BEARING, read by `collect` itself, where both copies had it as a documentation-only tuple beside `collect`'s own string literals — so the advertised set and the implemented one cannot drift. **Folding names TWO reasons, not one:** `train/loss_step` is a genuine RESULT, folded because a one-row-per-run table cannot show a finer axis, so calling it bookkeeping in the footer would mislabel it. Hidden is never DROPPED — `--all` restores everything and the footer always says what went and how to get it back. **`render` takes a `note`** because an empty table from a write-only backend reads as "the sweep recorded nothing", which is a different and much worse claim than "this tracker cannot be read from here". Rationale: `docs/architecture.md` record 8. Pins: `tests/test_sweep.py` (43 — the fold rules, the naming incl. the wiped-tracker restart, the CSV reader, the unreadable-tracker notes, the module main), `tests/test_sweep_runner.py` (22 — the spec's loud validation, the three-mode matrix, the default cell command, env scoping, failure isolation with report-before-exit, per-tracker experiments, dry-run).
- **The Run Manifest Is The UNION; A Native Slot Is A PROJECTION (`matrainer.tracking.manifest`, 2026-08-01):** SHIPS end to end — the accumulator, the capture sources (`capture_environment` / `capture_code` / `capture_config`, backed by `tracking/provenance.py`), `Tracker.log_manifest`, the MLflow + TensorBoard native projections, and `log_run_context` as the ONE orchestration entry (it fills a manifest, projects it, and RETURNS it; `capture_log_file(trackers, manifest=…, status=…)` finishes it). **`capture_log_file` ALSO ends the run on every tracker (`Tracker.finalize(status)`, 2026-08-02) — and that belongs here, not in each consumer.** Nothing called `finalize` anywhere until a real MLflow sweep showed eleven of thirteen FINISHED runs as `RUNNING` with no end time: the same run said `success` on disk and in-flight in the UI, and no backend could report a duration. The two that looked right did so BY ACCIDENT — a Lightning consumer adapts its trackers into `pl.Logger`s and Lightning finalizes those itself. This function already stated the terminal status and already looped the trackers, so putting it here fixed all eight consumers at once; a per-consumer call would be eight chances to forget and eight places for the tracker's status to disagree with the manifest's. **Finalizing is LAST**, after the artifact and manifest pushes, because a backend with a run lifecycle stops accepting writes once closed — MLflow tolerates a late write (measured: the metric lands, status stays `FINISHED`), `WandbTracker` does not (its `finish()` drops the run handle, so the next access starts a NEW run), which is what the `finalize=False` escape hatch is for. Pins: the ordering + escape-hatch tests in `tests/tracking/test_provenance.py`, and consumer-side `test_the_terminal_call_is_the_one_that_ends_the_run`, which forbids a backend calling `finalize` for itself. `manifest.py` + `provenance.py` are both at 100% coverage. Contract in `docs/architecture.md` record 3. **The base `log_manifest` projects `params` via `log_hyperparams`** — the one native slot EVERY backend has, so it belongs in the default, not in each override; an override calls `super()` FIRST and then adds its own slots (rule 2 is "also", never "instead"). **`primary_code()` may return `None` ON PURPOSE:** a backend with ONE source-commit field cannot hold the manifest's LIST, so the narrowing is ordered (repo containing the cwd -> repo containing the entry script -> a lone record) and declines when none applies. Do NOT "fix" that by falling back to `entries[0]` — it previously did, and a real MLflow run got an unrelated workspace package's commit stamped as `mlflow.source.git.commit` purely because it sorted first (found by running it, not by a test). An empty native field sends the reader to the manifest; a wrong one looks exactly like a right one. Three implementation rules the capture side encodes and that must not be undone: (a) **`capture_code` returns a LIST** — `code_state()` discovers editable installs via PEP 610 `direct_url.json` and dedups by git toplevel, because a run's behaviour is set by every editable package on `sys.path`, not by the CWD repo `get_git_commit_hash()` sees; (b) **`environment_snapshot` REDACTS** any name matching `SECRET_MARKERS` (TOKEN/KEY/SECRET/PASSWORD/AUTH/…) — the manifest is an uploaded artifact, so a captured `WANDB_API_KEY` would be a secret published to every backend; keep the NAME (that a token was set is provenance), drop the value; (c) **`accelerator_state` reads `sys.modules.get("torch")`, never `import torch`** — importing a framework to ask what device it uses would make a light tracking call pay a multi-second import, or pull in a framework the process deliberately did not choose. `config_params` is now the ONE hyperparameter derivation (it keeps scalars + all-scalar lists, and drops objects because a repr carries a memory address that would make identical runs diff); a consumer re-deriving its own is the divergence this ended. The three contract rules, in order of how easily they get broken: (1) **every static fact lands in the manifest unconditionally**; (2) a backend with a native home for a fact ALSO writes it there; (3) **no fact is ever native-only** — the moment one is, the same run tracked two ways stops being comparable and moving between backends silently loses fields, which is the entire reason this exists. **Three additions on 2026-08-02, all under the SAME rules:** (a) **`command.line`** — the invocation as a shell snippet a person can PASTE to rerun, `cd <cwd>` included so a relatively-referenced config resolves. It exists because `argv` alone CANNOT be pasted back: the workspace's runner is launched with `-m`, whose `argv[0]` is the module's FILE path (`.../recordstream/cli.py`) and does not re-execute — so `command_line()` detects the launch shape (`__main__.__spec__` set -> `-m <module>` with a trailing `.__main__` stripped; a non-`.py` executable -> pasted verbatim, since a console script carries its own shebang; else the interpreter in front) and `shlex.join`s it against the absolute `sys.executable`. Both fields STAY — `argv` is what `primary_code()` parses — and `line` is OMITTED, never guessed, for `argv[0] in UNREPRODUCIBLE_ARGV0` (`""`/`"-"`/`"-c"`, where the code never reaches `sys.argv`). Verified by pasting a real manifest's line from `/` and watching the training rerun. (b) **`capture_packages()`** -> `environment/requirements.txt` + `env.packages = {path, sha256, count, tool}`. `uv pip freeze --python <sys.executable>` when `uv` is on PATH, else `pip freeze`: MEASURED 0.063 s vs 0.963 s on 730 distributions, and this runs on every tracked run — `--python` pins the environment so cwd and activation are irrelevant. Nothing is lost by preferring uv: the two disagree only on how they spell an editable install, and pip's frozen commit cannot express `dirty`, which `code_state()` already records. Every failure (no pip, non-zero exit, timeout) is a debug log + `None`. (c) **`capture_datasets(runnable)`** -> the `datasets` section, which was EMPTY on every manifest ever written because `record_dataset` had zero callers workspace-wide. It walks the runnable with **`configured_slots`**, a deliberately DIFFERENT walk from `config_params`' — that one flattens to leaf SCALARS (a hyperparameter is a value), this one needs the OBJECTS (what identifies a dataset is a source) — and asks each via recordstream's `dataset_uri`/`dataset_url`, which follow `.source` wrappers themselves. **`kind`/`name`/`split` are DERIVED from the URI** (scheme / path / `split` param), so matrainer learns nothing source-specific and a new source type needs no change here; entries dedup by URI keeping the FIRST (outermost) slot, which is why recordstream propagates a view's URI verbatim. All three are called from `log_run_context`, NOT by each consumer — the same argument that put `Tracker.finalize` in `capture_log_file`: ten runnables already reach this function, and a per-consumer call is ten chances to forget. (d) **`capture_models(runnable)`** -> the `models` section, empty for the same reason `datasets` was (`record_model` had zero callers). It reuses the SAME `configured_slots` walk and the same URI-derived `kind`/`name`, but the PROTOCOL it reads has a deliberately different SHAPE, and that asymmetry must not be "tidied away": a dataset source exposes two plain strings because it reads ONE dataset, while a model wrapper exposes a LIST (`matrainer.uri.model_refs`) because it COMPOSES artifacts — a backbone fine-tuned from a checkpoint used two, and each `ModelRef` carries the `role` it played (`pretrained` = from outside the run, `checkpoint` = from a previous run of ours). A pipeline composing several models is the same shape one level up, which is why plural was chosen over "checkpoint wins". **`matrainer/uri.py` is TOP-LEVEL and stdlib-only** for the `metric_slots` reason — nine model wrappers across four consumer projects import it, several on deliberately framework-free backends — and NOT re-exported from the package root, which is the tracking surface. `hf_model_ref` is the ONE spelling of `hf://models/<id>` shared by the five wrappers that resolve to the Hub (mirroring recordstream's `hf://datasets/`), so they cannot drift into three formats that stop comparing equal for the same weights. **TWO invariants that are easy to undo and were both found by RUNNING it:** (1) **reporting an EMPTY list is an answer** — the walk stops at any object that implements the protocol, because falling through follows `.model`, which on `HuggingFaceModel` / `KerasModel` is a property that BUILDS; the guard is `refs is not None`, never truthiness (caught by a consumer test: a `pretrained=False` model raised *"num_classes is not set"* from inside a provenance read). (2) **asking never builds** — `_materialize` flows a deferred `Fluid` marker ONLY, never a live object, because `flow()` on a live object runs `solidify()`, which downloads weights and raises when the runnable has not injected `num_classes` yet. recordstream's `dataset_uri` was narrowed the same way in the same change. **(3) A FRAMEWORK-HELD child is still a slot — `configured_slots` reads `_modules`, not only public `__dict__` keys (2026-08-03).** `torch.nn.Module.__setattr__` diverts every Module-valued assignment into `self._modules`, keyed by the attribute name the caller used, so `self.model = TimmModel(...)` leaves `model` ABSENT from `__dict__` entirely — and the walk's "public attributes only" rule then made the model of EVERY torch-based runnable invisible. The manifest wrote `models: []` while `datasets` (a plain attribute, so still in `__dict__`) filled correctly: a complete-looking run, a green suite, and not one weight named. Found by READING A REAL RUN'S MANIFEST, which is the only place it was visible — every unit test passed, because a hand-built fake stores its attributes normally. `_CHILD_REGISTRIES` is the narrow exception to the underscore rule and is justified by one property: its KEYS are the public names the caller assigned, so nothing private is exposed. It is detected STRUCTURALLY (a `_modules` attribute that is a Mapping), never by an `isinstance` against `torch.nn.Module` — the same reason `accelerator_state` reads `sys.modules` — and a real public attribute always wins over a same-named child, so no slot is yielded twice. Pins: the framework-held-child group in `tests/tracking/test_provenance.py`, whose fake REPRODUCES the diversion rather than storing attributes normally (a fake that does not is exactly what let this ship). Per-wrapper spellings: timm resolves the exact tagged repo via `timm.get_pretrained_cfg(name).hf_hub_id` (static registry — 0.0000 s, offline, `None` for an unknown name), a Hub id is itself, and a zoo with no repository page (`keras://applications/…`, `smp://<arch>/<encoder>?weights=…`, `rfdetr://<variant>`, `ultralytics://yolo26n`) names the registry + entry and reports NO url rather than inventing one. (e) **PORTABLE PATHS — `$PROJECT_ROOT` / `$DATA_ROOT` / `$MODEL_ROOT` (`PORTABLE_ROOT_VARS`):** where one of those vars is SET, every absolute path under it is recorded as `$NAME/...`, so a manifest read on a machine that keeps its code/data/models elsewhere still points at the right things. **It is applied ONCE over the WHOLE document — in `to_dict()` AND `section()`, never at a capture site** — so a section added later is portable without anyone remembering, and so what is WRITTEN and what a native projection READS cannot disagree (a hosted backend's dataset field holding an absolute path beside a portable artifact is exactly the drift record 3 exists to prevent). **`os.path.expandvars` is the EXACT INVERSE** (pinned by `test_expandvars_is_the_exact_inverse`) — that is what makes contracting a whole document safe rather than lossy, and `contract_roots` is idempotent so a double application is harmless. **`env.roots` is the ONE skipped subtree (`PORTABLE_SKIP_KEYS`)**: it is the expansion table, and contracting a definition into a reference to itself would destroy the only record of what the root WAS — a reader without the vars set has nothing else to resolve from. Matching is on a path BOUNDARY (`/store` must not swallow `/storefront`) and the LONGEST root wins (a `MODEL_ROOT` nested inside `DATA_ROOT` resolves to the nearer one) — both pinned. **The quoting of `command.line` changed WITH this and the two cannot be separated:** `shlex.quote` wraps a `$` in SINGLE quotes, where it is a literal dollar sign — so the contracted line would have looked right and pointed at a directory that does not exist. `_quote` double-quotes any word carrying a variable (the shell expands inside those, and the expansion may itself contain a space, so bare is not an option either). Set no root and NOTHING changes — contraction is opt-in by configuration. **The SUITE must not inherit a root from the shell it was launched in (`tests/conftest.py::no_ambient_portable_roots`, autouse, 2026-08-03):** the workspace activation script (`source project.bashrc`) exports `PROJECT_ROOT`, and `sys.executable` lives under it, so every test comparing `command_line()` against a raw `sys.executable` failed in an activated shell and passed in a bare one — six failures in CI with nothing wrong in the code under test, which is the most expensive kind of red. Contraction is opt-in by CONFIGURATION, so a test that does not configure a root must not get one; a test that wants one sets it itself (the `roots` fixture), and an explicitly requested fixture is set up after an autouse one at the same scope. Do not delete that fixture to "simplify" the conftest. (f) **A LOCAL artifact carries `size` + SHA-256 `digest` (`local_file_facts`, 2026-08-03)** — the question `record_model`/`record_dataset`'s long-unfilled `digest` field exists for: is the checkpoint still on disk the one the run loaded? Applied to `file:` URIs in BOTH `configured_models` and `configured_datasets`. THREE deliberate non-answers: a REMOTE reference gets neither (identified by URI + revision; fetching gigabytes to fingerprint it would be absurd), a DIRECTORY gets neither (a SavedModel / imagefolder has no single content hash, and walking one to invent a composite is unbounded work at every run start), and a file above `MAX_DIGEST_BYTES` (2 GiB) keeps its `size` and skips the digest. `size` is free (one `stat`) and recorded ALWAYS, so an over-cap file is still distinguishable. Measured 1790 MB/s, so the default cap costs at most ~1.2 s. The facts are computed from the RAW absolute URI in `configured_*`, BEFORE the manifest contracts it — a `$MODEL_ROOT` path would stat nothing. **A referenced artifact must TRAVEL with the manifest:** `RunManifest.artifacts()` lists the side files (`config/final.yaml`, `environment/requirements.txt`) and the base `log_manifest` uploads them, skipping any already inside `log_dir`. This closed a live gap — `config/final.yaml` had been written since the manifest landed and NEVER uploaded, invisible on a file-backed backend (where it happens to sit in the right tree) and simply missing on every remote-only one, which is rule 3 broken by omission. `_write_artifact(relative, text)` is the ONE side-artifact write both callers use; do not re-hand-roll it. Serialization is `manifest.yaml` **and** `manifest.json` from ONE atomic write (temp + `os.replace`) after EVERY mutation — crash-safety is a WRITE POLICY, not a shutdown hook, so an interrupted run leaves a complete record and the `atexit`/`SIGINT`/`SIGTERM` handlers only stamp the terminal `status`. Never buffer until run end. YAML is `yaml.safe_dump(..., sort_keys=False)` — plain and TAG-FREE: confluid's dump emits `!class:` / `!ref:` / `!clone:` that only its own resolver reads, so the resolved config goes to its OWN `config/final.yaml` artifact referenced by digest, never inlined (the same "we log it, we don't re-own its FORMAT" rule as `matrainer.artifacts`). `pyyaml>=6.0` is a DECLARED core dep (it was previously reachable only transitively through confluid — a module that imports a package must depend on it); do not drop it back. Code provenance becomes a LIST (one record per editable distribution), because a run's behaviour is set by every package on `sys.path`, not by the CWD repo `get_git_commit_hash()` happens to see. The only new `Tracker` method is `log_manifest(manifest)`, defaulting to serialize + `log_artifact` — no wrapper layer over `Tracker` (that rule still holds).
- **Dataset + Model Lineage Reach The NATIVE Slots Too (`_project_datasets` / `_project_models` / `_project_inputs`, 2026-08-03):** with `datasets` and `models` finally populated, MLflow and W&B get them in their OWN lineage surfaces — rule 2 ("also", never "instead"): the union artifact still carries everything. **MLflow:** datasets are `DatasetInput`s and models are `LoggedModelInput`s, which need a logged-model ID, so `create_logged_model` makes the entity from METADATA ALONE first — no weights uploaded, the Model Registry untouched, every manifest field riding along as a tag. **W&B:** both sections become typed `Artifact`s marked `use_artifact` (that IS the lineage graph), with `add_reference` when the URI names a location W&B can address — a reference records WHERE the bytes live rather than uploading them. **THREE library behaviours that read as bugs if you do not know them, all MEASURED, all pinned:** (1) **MLflow does NOT dedup a logged model** the way it dedups a dataset input by digest, and `log_manifest` runs at least TWICE per run — so `MlflowTracker._logged_models` (URI -> model id) is what keeps every model from appearing twice; deleting it looks harmless and silently doubles every run's lineage. (2) **Both libraries restrict entity NAMES to sets that exclude every separator a real identifier uses** — MLflow rejects `/ : . %` and quotes outright (`Invalid model name`), W&B allows only alphanumerics/dashes/underscores/dots, so `timm/resnet50.a1_in1k` is refused by BOTH; the name is a sanitised LABEL (`_logged_model_name` / `_artifact_name`) and the exact identifier lives in the tags/metadata. (3) **`wandb.Artifact.add_reference` IS NOT FATAL and gets its OWN `try` (`_add_reference`, 2026-08-03).** It VALIDATES eagerly — a `file://` path not on this disk raises `ValueError`, and an `http(s)://` URI is FETCHED (a 404 raises `HTTPError`) — and it used to share the caller's `try` with `use_artifact`, so a reference failure skipped the registration too and the entry VANISHED from the lineage graph rather than degrading to the metadata-only form a zoo URI already gets. The artifact is the record; the reference is only an optimisation on top of it. **The URI is `expandvars`-ed before referencing, and that half is not optional:** the manifest is PORTABLE, so with `MODEL_ROOT` set a checkpoint's URI is stored as `file://$MODEL_ROOT/last.ckpt` — deliberately not a path anywhere — meaning a checkpoint reference could NEVER resolve on a machine that has the roots configured, which is every machine that sets them. `expandvars` is the documented exact inverse of `contract_roots`. Found by driving the REAL wandb library rather than the fake, which accepted any path — so the fake now enforces the must-exist rule too, since a fake that does not is what let this ship. **`wandb.Artifact.add_reference` REFUSES an unknown scheme** (*"You must pass name=… when tracking references with unknown schemes"*), so a zoo URI (`hf://`, `smp://`, `ultralytics://`) is metadata-only and only `REFERENCEABLE_SCHEMES` become references. Also: `model_type` reads `kind` **or** `source`, because `capture_models` writes the first and the manual `record_model` takes the second. **Reading it back, `client.get_run(run_id).inputs.model_inputs` is the query that works — `search_runs` returns runs whose `model_inputs` is EMPTY while `dataset_inputs` is populated**, so verifying lineage that way shows datasets landing and models silently missing, which is a convincing-looking bug in code that is doing the right thing (it cost a full debugging pass; the docstring says so too). Verified against a REAL sqlite MLflow store (two `log_manifest` calls -> 1 dataset input + 2 model inputs, not 2 and 4) and the REAL wandb library's validators, not only the fakes. Pins: the model-lineage group in `tests/tracking/test_mlflow_backend.py` and the lineage group in `tests/tracking/test_wandb_backend.py` — whose fakes ENFORCE the real name rule and the real `add_reference` scheme rule, so a dropped sanitiser fails there instead of only in production.
- **`log_text` Is The THIRD Content Channel, And Its Default Is REAL WORK (`Tracker.log_text`, 2026-08-01):** `log_metrics` takes numbers and `log_figure` takes images; a run value that is NEITHER — a confusion matrix rendered by `render_matrix_as_table`, a classification report, a diff — had no channel at all, so a consumer computing one could only put it in the log and a tracked run recorded the scalars beside it as though that were the whole result. `log_text(name, text, step=None)` is that channel. **Unlike `log_figure`, whose base implementation is a debug-logged skip, this default DOES the work** — text is trivially serializable, so the ABC writes a `.md` file under the backend's own `log_dir` (or, for a remote-only backend with no tree, into `save_dir` followed by `log_artifact(..., artifact_dir="text")`) and a caller never has to ask whether THIS backend can hold a table. The artifact call is skipped when the file is already inside `log_dir` — the same rule `log_manifest` applies, and without it a file-backed backend writes the same text twice into one tree. **A backend with a native text channel overrides and uses it INSTEAD, which is the OPPOSITE of the `log_manifest` rule and deliberately so:** there the artifact is a UNION guarantee that keeps two differently-tracked runs comparable, so a native slot is written "also, never instead"; here the text IS the payload and one durable home per backend is the entire requirement, so a second copy is just a second copy. The natives: MLflow `client.log_text` (writes the artifact itself), TensorBoard `add_text` (the Text tab, `step` driving the slider — durable in the event file, so the `.md` twin would add nothing), Aim `aim.Text` tracked as a sequence, and ClearML **`upload_artifact`, NOT `report_text`** (its text primitive writes to the task's CONSOLE stream, where a per-epoch table is interleaved with everything the process printed and cannot be compared between tasks). Cell annotations stop past 25 classes — unreadable by then, and the cost grows with N². Pins: the `log_text` group in `tests/tracking/test_base.py` (default file, remote upload, per-step files, group fan-out) + one per native backend + `tests/tracking/test_render.py` (the renderer had shipped with NO tests until it acquired a consumer; the pyplot-registration check is the one that would catch a "simplification" to `pyplot.subplots`).
- **A PER-CLASS VECTOR Gets Its OWN Renderers, Not The Matrix Ones — `per_class_vectors` / `render_vector_as_table` / `render_vector_as_figure` (2026-08-03):** `scalar_metrics` drops two shapes, not one: a square `N×N` confusion matrix AND a length-`C` per-class vector (what `average=None` produces). The matrix pair shipped 2026-08-02; the vector pair completes the set, and it is a SEPARATE pair rather than a widening of the first because a per-class metric is not a degenerate matrix — it has ONE axis of meaning, its values share a scale (they are all fractions), and what a reader wants from it is a RANKING. So the table is sorted **worst-class-first** and the figure is a horizontal BAR CHART with the mean as a dashed reference line, where the matrix renderers give class-ordered rows and a heatmap. A `1xC` heatmap strip would answer "which class is the model worst at" by making the reader decode colours against a colorbar. **`per_class_vectors` is the SELECTION rule and it matches by SHAPE, never by metric NAME** (a flat numeric sequence of length >= 2): a runnable emits scalars, vectors and matrices in ONE `compute()` mapping with no knowledge of which is which, so a name-based rule would need every consumer to agree on a convention nothing enforces. Scalars fall through (a scalar belongs in `log_dict`) and so do matrices, which is what lets the SAME mapping be handed to both selection rules with each taking only its own. **It lives HERE, beside its renderers, rather than upstream beside recordstream's `confusion_matrices_payload`** — that one exists because a confusion matrix feeds a GUI VIEWER and needs a normalized payload; a per-class vector feeds no viewer and needs no payload, so its only consumers are the two renderers below it and a selection rule is best read beside what selects for it. Two implementation details are load-bearing and both have the same shape as the matrix pair's: the figure is built through `matplotlib.figure.Figure` DIRECTLY (a pyplot figure is registered in a process-global manager and leaks one per eval epoch), and the table passes FLOATS to `tabulate` with `floatfmt=".4f"` rather than pre-formatted strings — tabulate PARSES a numeric-looking string and reformats it, so `f"{v:.4f}"` would be silently re-rounded and the column would not have the precision it appears to ask for. A length mismatch between `class_names` and the vector falls back to INDEX labels rather than dropping the value, because it usually means a metric with its own axis (a per-threshold curve) rather than a bug worth hiding a value over. Pins: `tests/tracking/test_render_vector.py` (22 — the selection rule in both directions, the worst-first sort in table AND figure, the pyplot-registration check, the precision one).

The trade moves "you forgot the model" from a `TypeError` at construction to run time, so **`TrainerRunnable._require_model()` raises the clear error at the top of `run()`** — called from the neutral `run()` AND from each machinery base that overrides it (`torch.loop` / `keras.trainer` / `tensorflow.loop` / `fastai.learner`), after that base's own precondition (device resolve, engine check) so the more fundamental failure still wins. It keys off a SENTINEL (`_NO_MODEL_SLOT`), not `None`, so a runnable that declares no model slot is untouched. Without it the miss surfaced as `'NoneType' object has no attribute 'compile'` in the keras family. Pins: `tests/test_runnable.py` (both guard directions). - **What A Metric Is CALLED Is A PAIR Of Vocabularies, Not A Canonicaliser (`matrainer.metric_names`, 2026-08-04):** `MetricNames(target=…, renames=…)` parses a metric key with the SOURCE engine's `MetricVocabulary` and renders it with the TARGET's; `matrainer`'s own — `<split>/<name>`, `split ∈ {train, val, test}`, the shape `build_metric_collection(...).clone(prefix="val/")` already produces — is one entry in that table, not a privileged destination. It exists because **every tracker records the key it is handed, verbatim** (measured across all six backends), so a sweep training ONE config on eight engines lands one quantity in four columns: `val_loss` (keras/jax/mlx), `valid_loss` (fastai), `eval_loss` (a `transformers.Trainer`), `val/loss` (torch), plus Lightning's `train/loss_epoch`. **A one-way canonicaliser was rejected for two concrete reasons.** It cannot PARSE: an unprefixed `accuracy` is a TRAINING metric under Keras and a VALIDATION one under fastai (its `Recorder` computes metrics on the validation pass and prefixes none of them), so a table-free rule files one engine's val accuracy in the train column — a wrong number that looks right. And the other direction is a real ask: `target: keras` records every backend, torch ones included, in the spelling a team's existing dashboards query. **The argument split is what makes ONE config key work for eight backends:** `source` is passed per CALL by the code doing the reporting (only it knows which engine produced the names, and which split a bare key belongs to), while `target`/`renames` live on the `@configurable` object a top-level `metric_names:` key broadcasts everywhere. **Five invariants, each of which has a way to fail silently:** (1) parsing recognises the canonical `<split>/<name>` WHATEVER the source, so translation is idempotent — without it a helper applied at two seams writes `train/train/loss`; (2) rendering does NOT invert the base-name aliases (`val/accuracy` -> `val_accuracy`, never `val_sparse_categorical_accuracy`): those four spellings are what `compile()` expanded `"accuracy"` into, artefacts rather than names anyone writes, so a vocabulary spells the SPLIT and the base name stays canonical; (3) `epoch`/`step` are AXIS keys and pass through — prefixing `epoch` invents a second series for the x-value of every other one; (4) an unknown framework RAISES rather than falling back to canonical, because a fallback renames nothing and is indistinguishable from a config typo; (5) the rename lands on the copy going to a TRACKER, never on the dict the engine hands its own callbacks — `keras_tracking_callback` translates what it forwards while `logs` stays untouched, since a wired `EarlyStopping(monitor="val_loss")` must keep finding Keras's name. **Where it is applied for you:** `keras_tracking_callback` (`source="keras"`) and `TrackerLogger` (`source="lightning"`), both taking `metric_names=`; a hand-written loop calls `as_metric_names(self.metric_names)`, the one line that turns an unwired slot, a live object or a deferred YAML marker into a translator. Like `metric_slots` it is TOP-LEVEL and stdlib-only (plus confluid) so the framework-free backends can use it; UNLIKE it, it IS re-exported from the package root — it sits on the path metrics take to a tracker, and a YAML has to be able to name it. Do NOT move the translation into `Tracker.log_metrics`: a tracker cannot know which engine or which split produced a bare key, which is exactly why `source` is a per-call argument. Rationale: `docs/architecture.md` record 6. Pins: `tests/test_metric_names.py` (46 — every vocabulary both directions, the fastai split rule, idempotence, the axis keys), plus the naming groups in `tests/test_keras.py` and `tests/lightning/test_trackers.py`.
- **The Per-Split Metric-Slot RULE Lives Here, At The TOP LEVEL (`matrainer.metric_slots`, 2026-08-02):** `merge_metric_specs(shared, split)` (mappings merge by key so a same-named entry SHADOWS, sequences concatenate, incompatible shapes REPLACE, `None` on either side means "not chosen") + `union_metric_specs(shared, *splits)` for an engine that computes ONE set for several phases (`keras.Model.compile`, a `transformers.Trainer`'s `compute_metrics`) — where widening is the honest failure, because a metric computed on a split that did not ask for it is noise a reader ignores while a wired metric that silently reports nothing is a bug nobody can see. It moved UP from a consumer (`sonair/metric_slots.py`) when a SECOND task needed the identical rule on the same eight engines. **Why matrainer:** it is the metrics VOCABULARY, which this package already owns — `build_metric_collection` / `scalar_metrics` (`matrainer.torch`) and `write_metrics_sidecar` (`matrainer.artifacts`) — and what a "metric" IS still differs per engine (a torchmetrics template mapping, a list of `keras.metrics` objects, a list of fastai function NAMES), so only the COMBINATION generalizes and it is applied to whichever vocabulary the caller uses. **It sits at the TOP LEVEL and NOT under `matrainer.torch`, which is the whole point:** that subpackage requires torch, and this module imports **nothing but the standard library** precisely so the deliberately framework-free backends (JAX, MLX, Keras, any hand-written loop) can apply the rule without a torch import entering their dependency graph — several consumers AST-scan their own modules for exactly that regression. For the same reason it is NOT re-exported from the package root: the root is the TRACKING surface, and nothing here touches a tracker. Do not move it under a framework subpackage, do not add a non-stdlib import (`tests/test_metric_slots.py::test_the_module_imports_nothing_but_the_standard_library` reads the SOURCE with `ast`, so it fails wherever the mistake is made rather than only where the framework is installed), and do not let a consumer re-derive the merge inline. Pins: `tests/test_metric_slots.py`.
- **A Metric An OWNED Loop Cannot AVERAGE Gets A Confusion-Matrix Accumulator (`matrainer.metric_functions`, 2026-08-04):** `zero_confusion` / `accumulate_confusion` / `macro_f1` — the companion to `metric_slots`, which decides WHICH metrics a split measures where this one computes the ones a hand-written loop cannot get right by averaging. **The reason is measured, not stylistic:** a backend whose engine owns the loop gets stateful metrics for free (`update()` per batch, `compute()` once), while a backend whose loop WE own sees one batch at a time and the obvious `fn(logits, targets) -> float` averaged over the epoch is quietly wrong for anything per-class — on 10 classes at batch 32, batch-averaged macro-F1 reads 0.8849 where the true value is 0.9182, and 0.3032 where it is 0.3486. Three to five points, ALWAYS downward (a class absent from a batch scores 0 for that batch and drags the mean), and worse with more classes — which in a cross-framework comparison is a systematic penalty on exactly the engines that own their loop. So the loop keeps ONE `C×C` integer accumulator per split, whose size is set by the class count and not the dataset, and reduces once at the end — what `torchmetrics` does internally, which is what makes the two numbers comparable (`macro_f1` matches `sklearn.metrics.f1_score(..., average="macro", zero_division=0)` AND `MulticlassF1Score(average="macro")` exactly; pinned both ways). **TOP LEVEL, not `matrainer.torch`, and NOT re-exported from the package root** — both for the `metric_slots` reasons: that subpackage requires torch while the callers here are deliberately framework-free (numpy is the only import, and every engine that needs this already produces arrays numpy can read), and the root is the TRACKING surface. **Three invariants that are silent when broken:** (a) an out-of-range target id RAISES rather than wrapping — the flat `truth * C + prediction` index would fold a stray id into another class's counts, the totals would still add up, and the metric would still look plausible (the usual cause is an accumulator sized from a stale `num_classes`); (b) SINGLE-LABEL only, so a consumer must DROP a confusion metric on a multi-label run rather than approximate one — a multi-hot row has no single cell to land in, and a number under a name that means something else is worse than a gap because nothing downstream can tell; (c) counting is `np.bincount` on the flattened index, not `np.add.at` — the obvious spelling and roughly an order of magnitude slower, which is measurable once per batch. A consumer keeps the per-batch protocol for the metrics it suits and PARTITIONS by NAME, so only a NAMED metric can be confusion-based (nothing can know what a user-supplied callable would want accumulated). **The set grew to cover PER-PIXEL tasks on 2026-08-05, and the additions are DERIVATIONS from the same matrix rather than a second family:** `overall_accuracy` (micro accuracy — `trace / total`, what a per-pixel task calls PIXEL accuracy), `iou_per_class` (the `[C]` VECTOR a segmentation report renders worst-first) and `mean_iou` (its nan-skipping mean). Each agrees exactly with the torchmetrics equivalent (`MulticlassAccuracy(average="micro")` / `MulticlassJaccardIndex(average=None)` / `(average="macro")`), pinned in that direction. **A class present NOWHERE scores `nan`, not `0`** — it was never given a chance to be wrong, so a zero is a judgement the data does not support and would drag any mean over the vector; `mean_iou` skips them, which is what makes it match `average="macro"`. An all-absent matrix answers `0.0` rather than `nan`, because the caller puts the value straight into a `{name: float}` channel where a `nan` is a value a tracker records and nobody can read. **`accumulate_confusion` gained `ignore_index`** for the void class a per-pixel task carries, and the DROP HAPPENS BEFORE THE RANGE CHECK on purpose: both sentinels in the wild (torch's `-100`, SegFormer's `255`) are deliberately outside `[0, C)`, so checking first would reject every batch that has one. It agrees with torchmetrics' own `ignore_index=`, pinned. **The mean-IoU bias is WORSE than macro-F1's and differently shaped**, which is the measurement to keep: batch-averaging is not merely low, it MOVES WITH THE BATCH SIZE — 10 classes at accuracy 0.7 against an exact 0.5922 reads 0.6164 at batch 4 and 0.5798 at batch 32 — because a class absent from a batch is SKIPPED by that batch's mean rather than scored 0, so batches with fewer classes present are over-weighted. So it is not a constant offset a reader could learn to correct for, and the property to pin is BATCH-SIZE INDEPENDENCE (the same predictions give one number however they were fed in) rather than a direction. Rationale: `docs/architecture.md` record 7. Pins: `tests/test_metric_functions.py` (38, 100% coverage — mostly agreement tests against sklearn and torchmetrics, since restating the arithmetic would pass just as happily if code and test were wrong the same way).

- **System Metrics Are Framework-Free (`matrainer.tracking.system`):** `enable_mlflow_system_metrics` (the process-wide MLflow enable for `mlflow.start_run` clients), `start_system_metrics_monitor` (CPU/RAM/disk), and `MpsMetricsSampler` (a plain `start()`/`stop()` Apple-Silicon GPU sampler pushing nine `system/mps_*` scalars via `MlflowClient.log_metric`; torch + mlflow lazily imported; the inlined IOKit `PerformanceStatistics` reader replaces the buggy `apple-gpu` package). The Lightning `pl.Callback` wrappers over these live in `matrainer.lightning.callbacks`; a non-Lightning platform (raidar-ultralytics) calls the functions directly.
- **Random Run Names by Default (`matrainer.run_names.generate_run_name`):** The single helper for a random human-friendly `adjective_noun` slug (`coolname`, offline), used as the default `Tracker.run_name` and by consumers' merged classes. Empty prefix/postfix are skipped. Use it, not a bespoke timestamp/uuid. **The task→prefix mapping is `run_prefix(task)` beside it (2026-08-02)**, so the composed call `generate_run_name(prefix=run_prefix(task))` is the ONE line a merged train/evaluate/predict class writes — it had been an identical private `_run_prefix` in EIGHT of one consumer's backends. The mapping is deliberately MANY-TO-ONE (`fit`→`train`, `predict`→`predict`, everything else→`evaluate`): `evaluate` and `test` are two entry points but one KIND of run, and a name that said `test_funny_rabbit` for one and `evaluate_funny_rabbit` for the other would split one concept across two prefixes in every tracking backend. An unrecognised verb — including one a future runnable adds — resolves to `evaluate` rather than raising, because a run name is a LABEL and refusing to produce one is never the right answer to an unfamiliar verb. The PARAMETER is a plain `str` while the RETURN is the closed `RunPrefix` Literal, and that asymmetry is the layering: the task vocabulary belongs to the runnable (it is the `@entrypoint` set), the prefix set belongs here. Pins: `tests/test_run_names.py`.
- **The Runnable Protocol Lives in recordstream, Not matrainer:** `TorchRunner` (autograd marker), `ProgressReporting` (progress callback), the `entrypoint`/`runnable_entrypoints` method-annotation mechanism, the workflow combinators (`Sequence`/`Conditional`/`Switch` + predicates), and `DatasetProcessor` all moved to `recordstream.runnable` / `recordstream.workflow` / `recordstream.processing` (see recordstream AGENTS). A consumer's merged train+eval class inherits `TorchRunner`+`ProgressReporting` from recordstream and annotates its `fit`/`evaluate`/`test`/`predict` methods with `@entrypoint`. There is no `matrainer.runner`/`matrainer.progress`/`matrainer.workflow`/`matrainer.processing`.
- **The Trainer CLI Is A FACTORY; A Project CLI Is Its DATA (`matrainer.cli`, 2026-08-07 — P4):** four task projects carried ~280 near-identical CLI lines each (measured — they differed in the FRAMEWORKS table, the verb help texts, and nothing else that was not a docstring), plus a duplicated PEP 562 resolver in every package root. `matrainer.cli` is the machinery: `Framework(description, registrations)` (registrations is `None` / one module / a TUPLE — a tuple makes a multi-module coupling readable IN the table), `VERB_TASKS`, `default_dispatch` (materialize → the verb wins over the YAML `task:` → the TASKLESS-FIT GUARD: no `task` attribute runs as-is for `fit` only, other verbs RAISE naming the class — generalized from the one project whose upstream-loop backend needed it), `make_trainer_app(name, description, frameworks, verb_docs, dispatch)` (three `flow_mode="manual"` verbs from a factory — never a default-argument closure — plus the `frameworks` listing when a table is given; `dispatch=` is the extension point), and `trainer_main(app, frameworks)` running the established pre-step ORDER: `requested_framework` (from argv — the config is not loaded yet) → `pin_keras_backend` (BEFORE any registration import binds an engine) → `register_frameworks` (BEFORE `app.run()` — the eager `!class:Foo()` form builds during config load; best-effort, a partial install's absent registrations are correct) → `normalize_framework_flag` (REWRITTEN to `--scope framework=…`, never appended) → `app.run()`. Each arrow was a real bug when reversed, and the order is pinned ONCE here (`tests/test_cli.py`, incl. a source-read of `trainer_main`'s body) instead of per project. A consuming project's `cli.py` is its TABLE + two calls; do NOT reintroduce per-project copies of the dispatch/rewrite/pin helpers, and do NOT teach the factory a TASK — verb docs naming one come in through `verb_docs=`. The package-root twin is **`matrainer._exports.lazy_exports(__name__, _BACKEND_NAMES)`** — the resolver is matrainer's, the name table stays project data; an EMPTY extra marks a core name whose ImportError passes through untranslated. Rationale: `docs/architecture.md` record 10. Pins: `tests/test_cli.py` (25) + `tests/test_exports.py`.
- **ONE Binary — the `matrainer` Console Script: Generic Verbs + the Sweep Group (2026-08-07, user-authorized revision of the no-binary rule):** matrainer ships exactly one console script (`[project.scripts] matrainer = "matrainer.console:main"`), and its scope is closed: `matrainer train|evaluate|predict <config.yaml>` — the GENERIC runner over any project's `runnable:`-rooted config — plus `matrainer sweep …`. Since P4 (2026-08-07) the console is BUILT FROM `matrainer.cli` — `make_trainer_app(frameworks=None)`, which skips the `frameworks` listing a project CLI gets — so the generic verbs and the per-project CLIs are the same machinery by construction, not by mirroring. The behaviours (`recordstream.cli.materialize_runnable`, NEVER a bare `flow()` — a bare flow drops every top-level key silently; the verb→task map with the verb winning over the YAML's `task:`; `--framework` REWRITTEN to `--scope framework=…`, never appended; the keras engine pin `--framework tensorflow` → `setdefault(KERAS_BACKEND)` BEFORE anything imports keras; a runnable with NO `task` attribute runs as-is for `train` only, the other verbs raise naming the class) live on the factory. It works because every shipped example/sweep config spells its classes MODULE-QUALIFIED (verified — bare registered names occur only in comments); a config that does use bare names passes `--registrations mod1,mod2`, which is stripped from argv before liquifai sees it. The per-project CLIs REMAIN the ergonomic task-aware surface, and `recordstream run` remains the task-free generic one — this binary exists so a project-agnostic caller (the sweep, CI, an operator with a config in hand) needs neither. Do NOT grow it task verbs, a FRAMEWORKS table, or registrations knowledge — those stay per-project. Pins: `tests/test_console.py` (the `--registrations` strip, the pin-before-registrations ORDER, the sweep dispatch, no-frameworks-command, and an end-to-end `matrainer train` subprocess proving broadcast + verb-wins); the verb machinery itself is pinned in `tests/test_cli.py`.
- **Light Core Install + Extras:** `pip install matrainer` = confluid/liquifai/loggair/coolname/numpy only; `import matrainer` must NOT import torch or pytorch_lightning. Everything else is behind `[torch]` / `[lightning]` / `[mlflow]` / `[tensorboard]` / `[wandb]` / `[tensorflow]` / `[all]`. When adding a backend/helper that needs a heavy lib, gate it behind an extra + a lazy `require(...)`.
- **RecordStream Lineage:** Training data flows through recordstream **records** — plain dicts of typed values. Matrainer neither reshapes nor re-collates them: batching (`collate_records`), its read-back (`batch_tensor` / `batch_metadata`) and dataset normalization (`ensure_record_dataset`) are all recordstream's. If you find yourself writing a collate or a batch reader here, it belongs there.

# Marainer Mandates

## Current state

A PURE experiment-**tracking** library (v0.2.0) with a light core install: `marainer.tracking` (the `Tracker` ABC + four lazily-importing backends, provenance, system metrics), the optional per-framework helpers `marainer.lightning` / `.tensorflow`, plus `marainer.torch`, `.checkpoints`, `.run_names`, `.sinks`. No training loop, no CLI — runs go through `recordstream run`; the runnable protocol, workflow combinators and `DatasetProcessor` live in recordstream. Data is the recordstream **record** (a plain dict of typed values): `collate_fn_with_metadata` wraps `recordstream.collate_records` (`target_key="class"`), `ClassificationPredictionsSink` threads plain record dicts.

- **Marainer Is a TRACKING Library — NO Training/Evaluation Code (2026-07):** Marainer contains ONLY functionality to *log and track* an ML run — parameters, git hashes, config artifacts, log files, figures, metrics values, and system metrics — for various logger libraries and various training platforms. It holds **no training loop, no `training_step`/`validation_step`/`test_step`, no trainer/evaluator class.** A class that uses `pytorch_lightning.Trainer` reads like a standard Lightning example and lives in the CONSUMER (sonair/deltaid/raidar), NOT here. The guiding invariant: *removing marainer should need only a couple of line changes in a consumer to keep it training* (losing the rich tracking, keeping loggair logging). Do NOT reintroduce a `LightningTrainer`/`LightningEvaluator`/`LightningMarainer` base class, step functions, a `run()` loop, or a marainer CLI. (This reverses the pre-2026-07 "training orchestrator" design.)
- **The `Tracker` ABC Is the Abstraction — One Backend per File, Lazily Imported (`marainer.tracking`):** `Tracker` (in `tracking/base.py`) mirrors the `pytorch_lightning.loggers.Logger` shape (`name`/`version`/`experiment`/`log_hyperparams`/`log_metrics`/`save`/`finalize`) plus the extensions `set_tags`/`log_artifact`/`log_figure`/`log_dir`; `TrackerGroup` fans out to a list. The four backends live one-per-file — `CsvTracker` (stdlib only, the always-available default), `MlflowTracker`, `TensorBoardTracker`, `WandbTracker` — and each imports its library **lazily inside its methods** via `marainer._imports.require(module, extra)`, so `import marainer` / `import marainer.tracking` pulls in NONE of them and a missing lib raises one clear `pip install marainer[<extra>]` error. Every Tracker is zero-arg constructible (workspace lazy-init rule): the native handle is built on first `experiment` access. The Tracker is "abstract enough" — do NOT add wrapper layers over it (an earlier `as_tracker`/`_LoggerTrackerView` machinery was removed). Backends are `@configurable`, entry-pointed `marainer-tracking`.
- **Three Optional Hookup Styles, Consumer Chooses (per framework / use case):** A standard Lightning class pulls in marainer tracking however fits — marainer offers ALL of: (1) plain **utility functions** — `marainer.tracking.provenance.log_run_context(trackers, params)` (git hash + config artifacts + params), `capture_log_file(trackers)`, and the system-metric helpers — called from the consumer's own run wrapper; (2) an optional **`pl.Callback`** — `marainer.lightning.TrackingCallback([tracker], params=…)` added to `pl.Trainer(callbacks=[...])`, logging provenance on fit/test start and the log file on end; (3) the **`TrackerLogger`** bridge — `marainer.lightning.TrackerLogger(tracker)` passed to `pl.Trainer(logger=…)` so a marainer Tracker receives per-step metrics like any pl logger. Metrics/curves may equally stay on stock `pytorch_lightning.loggers.*` — marainer USES pl loggers, never reimplements them. Don't collapse these to one — the choice is the consumer's.
- **`marainer.lightning` Is OPTIONAL Lightning Tracking Helpers, Not a Platform (`pip install marainer[lightning]`):** Behind the `[lightning]` extra (guarded `require("pytorch_lightning", "lightning")`). Contents: `TrackingCallback`, `TrackerLogger`, the system-metric callbacks (`MlflowSystemMetricsCallback`/`MPSMetricsCallback` + `activate_for_lightning`) which drive `marainer.tracking.system` sampling for a Lightning `MLFlowLogger` run, the progress bridge (`LightningProgressCallback`/`attach_lightning_progress`, mapping Lightning's per-batch hooks onto the `recordstream.runnable.ProgressReporting` sink), `build_checkpoint_callbacks` (translates the framework-neutral policies below into `ModelCheckpoint`s), and the metric utilities `build_metric_collection` / `coerce_metric_value` / `scalar_metrics` / `MetricPreset`. NO training-loop class. `marainer.tensorflow` mirrors this with `keras_tracking_callback`.
- **`marainer.torch` = torch-only, Lightning-free helpers (`pip install marainer[torch]`):** `load_lightning_checkpoint` (loads Lightning `.ckpt` / Ultralytics `.pt` / plain state-dict; strips the Lightning `model.` prefix; auto-retargets to a named child), `ensure_record_dataset` (normalize any wired source to a record-dict `Dataset` via a `recordstream.Stream`), `collate_fn_with_metadata` (a THIN wrapper over `recordstream.collate_records` that additionally stacks a wrapper-item `Label` target's per-record list into an `[N, …]` tensor — the one thing `collate_records` leaves as a list; the target key is the `target_key="class"` param; an array-item target like `Mask` is already stacked, plain entries survive as per-record lists; UNUSED by any workspace consumer today, kept for a non-Lightning torch trainer), and the torch BUILDERS for the prediction-output contracts (`classification_output` / `segmentation_output` — the contracts themselves moved to the neutral `marainer.outputs`, see the next mandate). These stay in marainer FOR NOW (user decision 2026-07) even though they aren't strictly tracking; a NON-Lightning platform (an Ultralytics trainer) uses them via `marainer[torch]` without pulling `pytorch_lightning`.
- **Prediction-Output Contracts Are FRAMEWORK-NEUTRAL; Only Their Builders Are Not (`marainer.outputs`, 2026-07-29):** `ClassificationOutput` / `DetectionOutput` / `SegmentationOutput` live in **`marainer.outputs`**, which imports NOTHING but `typing` — a consumer on Keras/JAX/TF must be able to declare its output contract without `pip install marainer[torch]`. Each is a **generic `TypedDict`** parameterized by the array type it carries (`ClassificationOutput[Tensor]` / `[np.ndarray]`; a bare name means "any array type", so existing torch call sites are unchanged). The BUILDERS stay per-framework because `softmax`/`argmax` are library calls, not type declarations: `marainer.torch.outputs.classification_output` / `segmentation_output`, which also RE-EXPORT the contracts (one import for a torch consumer, and `from marainer.torch.outputs import DetectionOutput` keeps working) — a re-export, never a second definition. Detection deliberately has NO builder: boxes come from the detector's interface, so the dict is built inline at the call site. This is the same split as `marainer.checkpoints` (neutral policies) vs `marainer.lightning` (the translation) and `marainer.torch.balancing` (the torch `weight=` convention). A new framework backend adds `marainer.<framework>.outputs` with its own builders; it does NOT redefine the contracts. Pins: `tests/test_outputs.py`.
- **Framework-Neutral Checkpoint Policies (`marainer.checkpoints`):** `CheckpointPolicy` base + `SaveLast` / `SaveEveryEpoch(every_n_epochs)` / `SaveBest(monitor, mode, top_k)` are declarative config carriers (zero-arg `@configurable`). Each framework subpackage translates them into its native mechanism — `marainer.lightning.build_checkpoint_callbacks` → `pytorch_lightning.callbacks.ModelCheckpoint`. Checkpointing is opt-in (no policy ⇒ the framework default). Add a new policy here; translate it in the framework helper.
- **Automatic Git Provenance (`marainer.tracking.provenance`):** `log_run_context` always stamps the `git.commit` tag (`get_git_commit_hash()`, `+ "-dirty"` on uncommitted changes) and the config-script path, and uploads the transitively-included YAML tree (`liquifai.context.included_paths`) as a `config/` artifact to every tracker. `capture_log_file` uploads the active loggair output file (`loggair.get_active_config()["log_file"]`) as a `logs/` artifact at run end. Consumers get this by calling the functions, or via `TrackingCallback` (Lightning) / `keras_tracking_callback` (TF). Don't hand-roll git/config/logfile logging elsewhere.
- **System Metrics Are Framework-Free (`marainer.tracking.system`):** `enable_mlflow_system_metrics` (the process-wide MLflow enable for `mlflow.start_run` clients), `start_system_metrics_monitor` (CPU/RAM/disk), and `MpsMetricsSampler` (a plain `start()`/`stop()` Apple-Silicon GPU sampler pushing nine `system/mps_*` scalars via `MlflowClient.log_metric`; torch + mlflow lazily imported; the inlined IOKit `PerformanceStatistics` reader replaces the buggy `apple-gpu` package). The Lightning `pl.Callback` wrappers over these live in `marainer.lightning.callbacks`; a non-Lightning platform (raidar-ultralytics) calls the functions directly.
- **Random Run Names by Default (`marainer.run_names.generate_run_name`):** The single helper for a random human-friendly `adjective_noun` slug (`coolname`, offline), used as the default `Tracker.run_name` and by consumers' merged classes (`generate_run_name(prefix=task→"train"/"evaluate"/"predict")`). Empty prefix/postfix are skipped. Use it, not a bespoke timestamp/uuid.
- **The Runnable Protocol Lives in recordstream, Not marainer:** `TorchRunner` (autograd marker), `ProgressReporting` (progress callback), the `entrypoint`/`runnable_entrypoints` method-annotation mechanism, the workflow combinators (`Sequence`/`Conditional`/`Switch` + predicates), and `DatasetProcessor` all moved to `recordstream.runnable` / `recordstream.workflow` / `recordstream.processing` (see recordstream AGENTS). A consumer's merged train+eval class inherits `TorchRunner`+`ProgressReporting` from recordstream and annotates its `fit`/`evaluate`/`test`/`predict` methods with `@entrypoint`. There is no `marainer.runner`/`marainer.progress`/`marainer.workflow`/`marainer.processing`.
- **Class-Imbalance Weighting Lives Here, Not In A Task Package (`marainer.torch.balancing`, 2026-07-29):** the inverse-frequency policy is THREE steps that belong together — `loss_accepts_weight` (does the loss take a `weight` arg; works on a live loss OR a deferred `Fluid`, so a trainer can skip the target walk), `inverse_frequency_weights` (the arithmetic; unobserved class -> 0.0 not inf, out-of-range ids ignored, `None` when nothing was counted so "no weights" is distinguishable from "all-zero weights"), and `apply_class_weights` (both + injection + the can't-balance warning). Extracting only the predicate is the half-move trap: the next consumer still reimplements the arithmetic and the injection. `apply_class_weights` RETURNS `(loss_fn, weights)` because a `Fluid` cannot be mutated in place — it is flowed with `weight=` and the caller MUST rebind. Callers pass ALREADY-ENCODED integer class ids: label->id mapping belongs to whoever owns the label map (recordstream's `LabelMap` in the classification case), which keeps this module free of any dataset dependency. It sits under `marainer.torch`, NOT the package root, because `weight=` is a `torch.nn` CONSTRUCTOR convention — Keras takes `class_weight` on `fit()` — so the subpackage split is the framework boundary. Pins: `tests/test_balancing.py`.
- **No CLI — Runs Go Through `recordstream run`:** The marainer CLI + `marainer.commands` plugin group are retired. A consumer's config roots at `runnable:` with a `task:` and runs via `python -m recordstream.cli run -c config.yaml`; consumers may also ship their own per-project CLI (`sonair lightning train`, `raidar evaluate`, …). Don't reintroduce a marainer binary.
- **Light Core Install + Extras:** `pip install marainer` = confluid/liquifai/loggair/coolname/numpy only; `import marainer` must NOT import torch or pytorch_lightning. Everything else is behind `[torch]` / `[lightning]` / `[mlflow]` / `[tensorboard]` / `[wandb]` / `[tensorflow]` / `[all]`. When adding a backend/helper that needs a heavy lib, gate it behind an extra + a lazy `require(...)`.
- **`ClassificationPredictionsSink` Stays (`marainer.sinks`):** The modality-neutral top-k JSON predictions sink (its own code is numpy-only — no torch/lightning logic) remains in marainer core, entry-pointed `marainer-sinks`. NOTE: it imports `recordstream` for the `Record` type, so `import marainer.sinks` transitively pulls torch — it is NOT part of the light-core import contract (only `import marainer` / `import marainer.tracking` are torch-free). It consumes per-record prediction mappings — a model MUST emit a per-record mapping (not a batched tensor) in predict mode.
- **RecordStream Lineage:** Training data flows through recordstream **records** — plain dicts of typed values. Marainer's torch helpers (`collate_fn_with_metadata`, `ensure_record_dataset`) preserve metadata — never bypass it.

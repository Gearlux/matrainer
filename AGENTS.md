# Marainer Mandates

- **`TorchRunner` Marks Gradient-Based Runnables (`marainer/runner.py`):** The base `LightningTrainer` inherits the stateless marker mixin `marainer.runner.TorchRunner` (re-exported as `marainer.TorchRunner`), which stamps the duck-typed `__torch_runner__ = True` class flag — so every task trainer (sonair / deltaid / raidar) inherits it for free. Its sole purpose: let a GUI executor that runs the graph under `torch.inference_mode()` (FluxStudio's `RunNode`, mirroring ComfyUI's grad-free node evaluation) distinguish "needs autograd" and re-enable it for the duration of `run()` — otherwise `loss.backward()` dies with *"element 0 of tensors does not require grad and does not have a grad_fn"* (model params, forward activations, and the loss are all inference tensors). **Inference-only runnables (`LightningEvaluator`, `DatasetProcessor`) MUST NOT inherit it** — they compute no gradients and run as-is. The marker is a pure mixin (no `__init__`, no state) so it composes cleanly with `pytorch_lightning.LightningModule`; FluxStudio reads the flag duck-typed (no hard `marainer` import). Don't bake ComfyUI/inference-mode knowledge into marainer — marainer only declares *that* a runnable needs grad; the executor decides *how* to honour it. Pins: `tests/test_runner.py`.
- **`ProgressReporting` Reports Run Progress Through a Comfy-Free Callback (`marainer/progress.py`):** Every long-running runnable — `LightningTrainer` (+ task subclasses), `LightningEvaluator`, `DatasetProcessor` — inherits the stateless mixin `marainer.progress.ProgressReporting` so a GUI executor (FluxStudio, driving ComfyUI's native per-node progress bar) can surface real progress WITHOUT marainer importing comfy. This mirrors the `TorchRunner` split exactly: marainer declares *that* a runnable can report progress; the executor decides *how* to display it. The executor injects a sink via `set_progress_callback(cb)` (a plain `Callable[[float, float, str], None]` = `(value, total, desc)`); the runnable drains it from its loop via `self._report_progress(value, total, desc)` — a **silent no-op when no sink was injected** (a plain `marainer train`/`evaluate`/`process` CLI run is byte-for-byte unchanged) and when `total` is `None`/non-positive (an unbounded/streaming length leaves the bar indeterminate; `_report_progress` never raises — a broken sink must never abort a run). **Lightning runnables get whole-run progress for free** via `LightningProgressCallback` (a `pytorch_lightning.Callback`): `LightningTrainer.run()` and `LightningEvaluator.run()` call `attach_lightning_progress(lightning_trainer, self)` right AFTER `flow(self.lightning)` — the SAME post-flow point `system_metrics.activate_for_lightning` appends its callbacks (Lightning iterates `trainer.callbacks` at hook-call time, so a post-construction append is honoured), a no-op when no sink is set. The mapping: **training** is ONE bar over the whole run — `value = trainer.global_step` out of `total = trainer.estimated_stepping_batches` (the planned step count across ALL epochs, honouring `max_epochs`/`max_steps`/`accumulate_grad_batches`/`limit_train_batches`), so it advances smoothly across epoch boundaries instead of resetting; standalone **test**/**predict** report the per-stage batch count; **validation is deliberately NOT reported** (during `fit` it interleaves with the global-step bar, and the runnables never call `validate()` standalone). `DatasetProcessor` reports per sample (`len(flux.source)` total) INDEPENDENTLY of its console `show_progress` rich bar — the native bar fires even when `show_progress=False`. The protocol is exposed via `marainer.progress` (NOT re-exported from `marainer.__init__`, which stays Lightning-import-free); FluxStudio consumes it duck-typed (`hasattr(runnable, "set_progress_callback")`), no hard fluxstudio→marainer coupling. Don't bake ComfyUI knowledge into marainer; a new long-running runnable inherits `ProgressReporting` and either uses a Lightning trainer (free) or calls `_report_progress` in its loop. Pins: `tests/test_progress.py`, `tests/test_processing.py` (callback-fires tests), `tests/test_training_scenarios.py::TestProgressCallback` (real-fit integration).
- **Generic Step Functions, Specialised Subclasses Allowed:** `LightningTrainer.training_step` / `validation_step` implement the generic `preds = self(batch.input); loss = self.loss_fn(preds, batch.target)` pattern, and per-task adapters (sonair classification, deltaid segmentation, the marainer-generic detection path in raidar) MUST conform to that shape on either side. When the task contract genuinely doesn't fit — most prominently object detection, where the model needs both images and targets in `forward` and where loss + predictions are produced together — a per-task subclass that overrides the step functions is permitted. See `raidar.lightning_trainer.LightningDetectionTrainer` for the canonical pattern. Subclassing solely to skip the adapter layer when the generic shape DOES fit remains a code smell.
- **Five-Verb Vocabulary:** The CLI exposes exactly five verbs — `train`, `evaluate`, `process` (escape hatch), `download`, `convert`. New verbs require user approval; resist verb proliferation. Use `_run_marainer_subcommand` for thin wrappers mirroring `train_model` / `evaluate_model` / `download_data` / `convert_data` in navigaitor.
- **Workflows Are Higher-Order Runnables (`marainer/workflow.py`) — NOT a new verb, NOT an external engine:** Composing several runnables (train → evaluate, "skip-if-cached") is done with Confluid-`@configurable` **combinators** that HOLD other runnables — the runnable-level analogue of SampleFlux's higher-order ops (`Parallel`/`TransformChain`/`Enable`): `Sequence` (run a list in order — the workflow), `Conditional` (run `if_true`/`if_false` by a `condition`), `Switch` (key a `selector` into `cases`+`default`), plus the no-arg-`__call__ -> bool` predicates `PathExists`/`Not`/`AllOf`/`AnyOf`. A workflow is therefore ONE Confluid document of `@configurable` runnables, dispatched by the **existing `process` verb** (`_dispatch_processor` runs any `.run()` object under `processor:`) — so it lights up CLI + navigaitor (MCP) + FluxStudio with NO bespoke glue and NO sixth verb (the Five-Verb mandate holds). Do NOT reach for an external workflow engine (Airflow/Prefect/Dagster) or ComfyUI-node-only control flow — the workflow lives in Confluid. **Invariants:** each combinator is `@configurable`, implements a no-arg `run()`, is **zero-arg constructible** and does NO work in `__init__` (the workspace lazy-construction rule); branches and conditions are stored as-is and **flowed lazily inside `run()`** (`flow(x) if isinstance(x, Fluid) else x` — the same pattern as `DatasetProcessor.run` / `Enable.__call__`), because a Confluid `!class:`/`!lazy:` member arrives as a deferred `Fluid` stub. **The guarantee `run()` provides: only the SELECTED branch's `run()` is ever called** — there is no execution-blocking and no dead branch; an enclosing `Sequence` continues to the next step regardless (the *memoise-and-continue* answer to "don't recompute, move on"). Wire a branch `!lazy:` so an unchosen branch is never even built (no model/dataset materialised). A `None` branch / `None` condition is a legal no-op (zero-arg safety). **FluxStudio canvas:** the combinators INHERIT `TorchRunner` + `ProgressReporting` so a workflow runs correctly under ComfyUI. A combinator may wrap a *trainer*, so it declares `__torch_runner__` (FluxStudio's executor re-enables autograd for the whole run — otherwise the inner `loss.backward()` dies under ComfyUI's `inference_mode`; autograd-on is harmless for an inner evaluator, which is why a combinator is NOT "inference-only" and the `LightningEvaluator`/`DatasetProcessor`-MUST-NOT-inherit rule does NOT extend to it). It also FORWARDS the executor-injected progress callback to whichever branch is running (`_run(branch, self._progress_callback)`), so the native per-node progress bar tracks the live step. The canvas wiring of a runnable INTO a combinator's slot is FluxStudio's **dual-mode runnable node** (the trainer/evaluator wired into `if_true`/`steps_N` is built-but-not-run, the combinator runs it — see fluxstudio AGENTS). Entry-pointed `marainer-workflow = "marainer.workflow"` (reinstall the editable after changing it — the entry-point staleness gotcha). A workflow compiles 1:1 to hand-written Python (`if cond: a.run()` / sequential statements). Pins: `tests/test_workflow.py` (order, selection, predicates, zero-arg construction, only-selected-runs, the non-runnable-branch `TypeError`, TorchRunner declaration + progress-forwarding, and a Confluid dump/load round-trip that runs a nested workflow); example `examples/workflow_convert_if_missing.yaml`.
- **Plugin Discovery via Entry Points:** Sibling projects register CLI verbs through `[project.entry-points."marainer.commands"]` and a `register(app)` callable. Don't fork the CLI; extend it.
- **Confluid-First Wiring:** Models, losses, datasets, loaders, callbacks, and trainers MUST be Confluid-`@configurable` so a single YAML drives the entire experiment. No code-only configuration.
- **Registered Lazy Runtime Members (`marainer.configurables`):** The select third-party runtime members a runnable defers — `torch.optim.Adam`/`AdamW`/`SGD`, `torch.utils.data.DataLoader`, `pytorch_lightning.Trainer` — are `register(..., lazy=True, group="optimizer"|"loader"|"lightning")`-ed in `marainer/configurables.py` (an import-only module, entry-pointed under `confluid.configurables`, re-exported via `__all__` so FluxStudio's `__all__`-pass surfaces them). `lazy=True` stamps `__confluid_lazy__` so FluxStudio generates OBJECT nodes that yield a deferred `LazyClass` (the trainer flows it with `params=` / `dataset=` at `run()`) and skip the runtime-injected required param. **No `category`** — only a presentation-only `group`: a `category` would resolve into a navigaitor form-spec picker offering the raw `params`-taking optimizer instead of navigaitor's curated `AdamWOptimizerConfig`; FluxStudio detects them via the `lazy` mark instead. These are NOT workspace classes, so they have no `@configurable` decorator — register them here, and after changing the set reinstall the editable so the entry-point metadata refreshes (`aisland setup`). Don't scatter `register` calls for runtime members elsewhere. **`configurables.py` ALSO surfaces two more canvas-only groups** (so FluxStudio's whole-graph YAML↔workflow converter, `fluxstudio.graphio`, can place a config's loggers + base trainer as nodes): (1) **Lightning loggers** — the stock `pytorch_lightning.loggers.TensorBoardLogger`/`CSVLogger`/`MLFlowLogger` are `register(..., role="logger", group="logger")`-ed — `role="logger"` (in the bridge `_MEMBER_ROLES`), **NOT** `lazy=True`, so they build EAGERLY (a logger's required `save_dir` stays a configurable widget instead of being skipped as a runtime-injected slot; loggers must stay `!class:` eager in YAML so the Lightning Trainer materializes them when it flows). (2) **Base runnables** — `marainer.trainer.LightningTrainer` / `marainer.evaluator.LightningEvaluator` are first-party (already `@configurable`), re-exported in `__all__` ONLY so FluxStudio's `__all__`-pass surfaces them as RUNNABLE nodes (same as the task trainers), making a config rooted on the generic base trainer importable. They're re-exported HERE — an import-only discovery module that already pulls Lightning — rather than in `marainer.__init__`, so a plain `import marainer` stays free of the Lightning import cost.
- **Minimal-Ctor Trainers/Evaluators + `!lazy:` Deferred Slots (confluid rule 4):** `LightningTrainer` / `LightningEvaluator` (and every specialisation — sonair / raidar / deltaid) take a **minimal constructor** — only the genuinely-required inputs (`model`/`train_set` or `model`/`dataset`) plus identity scalars (`num_classes` / `ignore_index` / `experiment_name` / `run_name`) — and do **no functional work** in `__init__`. Every deferred slot (`optimizer` / `train_loader` / `val_loader` / `test_loader` / `lightning` / `*_metrics`) is a **body attribute** defaulting to `LazyClass(...)`, configured post-construction (YAML / Confluid broadcasting / a subclass setting it). `run()` flows them — loaders with `dataset=`, the optimizer with `params=` (via `configure_optimizers`), `lightning` after the auto-`ModelCheckpoint` / logger wiring. `to_pydantic` introspects these body slots (confluid `_post_init_field_specs`), so they stay enumerable by navigaitor / MCP / FluxStudio. **YAML contract:** a deferred slot MUST be wired `!lazy:`, NOT `!class:` — a bare `!class:` post-init attr is eagerly materialized on assignment by confluid (it would build an optimizer with no `params`); confluid auto-defers such a misconfigured value WITH a warning, and `LightningTrainer._marainer_warn_eager_runtime_slots()` warns at `run()` if a slot arrived already-materialized. Do NOT reintroduce `optimizer=`/`*_loader=`/`lightning=` as constructor parameters; tests configure these via post-construction `setattr` (see `tests/test_default_checkpoint.py::_make_trainer`, `tests/test_evaluator.py::_make_evaluator`).
- **Normalize Sources to `Dataset[Sample]` via `ensure_sample_dataset` (the ONE guarantee):** `marainer.trainer.ensure_sample_dataset(source)` returns a map-style `Dataset` that is GUARANTEED to yield `Sample`s — a `sampleflux.Flux` is returned unchanged (it already coerces every item via `Sample.from_any` in `__getitem__`/`__iter__`, and this preserves a subclass's own wrap incl. its `label_names`); anything else (a `HuggingFaceSource`, another `torch` `Dataset`, a plain `list`, a stream of raw dict/tuple rows) is wrapped in a `Flux`, which makes it both a `Dataset` AND `Sample`-yielding. Calling it ONCE up front means the rest of the pipeline (target detection, label fitting/encoding, loaders, collate, metrics) can assume `Sample` items unconditionally — no per-call "is this a Sample?" checks. The base `LightningTrainer.run()` applies it to `train_set`/`val_set`/`test_set`; a task subclass that touches the datasets *before* `super().run()` (e.g. sonair's `initialize()`, which walks targets to fit a `LabelMap`) MUST call `ensure_sample_dataset` at the top of its `initialize()` so it operates on guaranteed `Sample`s too (it's idempotent — a `Flux` passes straight through). This is why a trainer's `train_set` param can be typed `Dataset[Any]` while YAML wires a non-`Dataset` source: the source arrives via the deferred Fluid path (confluid skips is-instance validation on Fluids) and is normalized at run time. Do the normalization through this ONE helper — don't hand-roll per-subclass wrapping. **Sibling helper `build_metric_collection(metrics, **flow_dims)`** (same module) is the ONE way to turn a task's `metrics` slot into a `MetricCollection`, and it accepts EVERY shape the slot can hold (so a GUI can wire a single metric node into it): a **`Mapping`** `{name: template}` is flowed per-value and keyed by name; a **ready-made `MetricCollection`** is returned as-is (never re-wrapped); **a single metric OR a `list`/`tuple` of them** — each a live `Metric`, a `LazyClass`/`Fluid` template, or a metric class — is flowed with `flow_dims` and wrapped in a `MetricCollection` (auto-named by class). The single-metric arm is load-bearing for FluxStudio: wiring ONE metric node's **`class` (`Lazy`) output** into the `metrics` slot now works (a bare `Lazy` used to crash with `'Lazy' object has no attribute 'items'`), and because it rides the deferred `class` output, `flow(template, num_classes=…)` sizes it off the model head at run time — NOT the `num_classes=0` widget the eager `instance` output would build from (a `MulticlassConfusionMatrix(num_classes=0)` raises). The caller clones the result per split. Both sonair's trainer and evaluator use it — don't re-inline the shape branching. **Non-scalar metrics (e.g. a confusion matrix) ARE allowed in the collection** — `test_step` logs only scalars (`numel()==1`) to Lightning and `computed_metrics` keeps only scalars via `_scalar_metrics`, but the full `compute()` (incl. the `N×N` matrix) reaches the metrics sidecar; the GUI display of a non-scalar metric is a separate `@output`/viewer concern, not a reason to reject it here.
- **Post-Run `@output` Contract — `computed_metrics` + `label_names` (base trainer AND evaluator):** Both `LightningTrainer` and `LightningEvaluator` declare two confluid `@output` properties (read-only, under `@property`; surfaced by `confluid.output_specs` to FluxStudio's Run-node results panel + navigaitor's form-spec). `computed_metrics` (`Dict[str, float]`) is **scalars only** — the trainer reads Lightning's `self.trainer.callback_metrics` (NOT the per-split `MetricCollection`s, which are reset each epoch), the evaluator reads `self.metrics.compute()` (the `test/`-prefixed collection, not reset); `label_names` (`List[str]`) returns the resolved class names (`[]` when none). **Both RAISE before `run()`** — the trainer guards on the Lightning back-ref `self.trainer` (raises pre-`fit`), the evaluator on `isinstance(self.metrics, MetricCollection)`. The trainer stashes names in `run()` as `self._label_names` (underscore-prefixed ⇒ never a config knob); the evaluator reuses `self._resolved_class_names`. **Name MUST be `computed_metrics`, NOT `metrics`** — `self.metrics` is the evaluator's `MetricCollection` body slot (and a sonair ctor param), so a read-only `@property metrics` would break `self.metrics = …`. The JSON-safe coercion helper **`_coerce_metric_value` lives in `marainer/trainer.py`** (relocated from `evaluator.py`, which re-imports it — trainer is the foundational module the evaluator already imports from, so no backwards dependency) alongside `_scalar_metrics` (coerce + drop non-scalars). Task subclasses inherit both outputs for free (`output_specs` MRO-walk); don't re-declare them. In FluxStudio every `@output` is a wireable output socket on the (self-running) trainer/evaluator node — `computed_metrics`/`label_names` ride `STRING` (JSON) sockets, alongside the object output `trained_model` (`@output` returning the live `nn.Module`). **The evaluator ALSO declares a third `@output`, `all_metrics` (`Dict[str, Any]`):** because `computed_metrics` is scalars-only, a NON-scalar metric (an `N×N` confusion matrix) would otherwise be invisible. Rather than a confusion-matrix-SPECIFIC output (an earlier `confusion_matrix` design that baked a "which metric is the confusion matrix" heuristic into the evaluator), `all_metrics` is GENERIC: it returns the FULL `_coerce_metric_value(self.metrics.compute())` — EVERY metric by name, scalars AND non-scalars (a matrix → a nested list), JSON-safe — and carries NO classifier knowledge. The CONSUMER extracts what it needs: FluxStudio's *Confusion Matrix* viewer (`fluxstudio.nodes.ConfusionMatrixViewerNode`) wires `all_metrics` in and pulls EVERY confusion matrix out via sampleflux's `confusion_matrices_payload` (the square-2D entries — there can be several), keeping the metric-shape knowledge in the viewer/sampleflux, not the evaluator. It raises before `run()` like the others and rides a `STRING` (JSON) socket. This is the sanctioned way to surface non-scalar metrics — keep `computed_metrics` scalar-only and dump the FULL results on a generic `all_metrics` output for a viewer to interpret, rather than one bespoke typed output per metric kind.
- **Random Run Names by Default (`marainer.run_names.generate_run_name`):** `run_name` defaults to `None` on `LightningTrainer` / `LightningEvaluator` (and the sonair specialisations) → `__init__` fills it with a random, human-friendly `adjective_noun` slug (`coolname`-backed, offline) prefixed `train`/`evaluate` — e.g. `train_funny_rabbit` — so every run is distinguishable in logs / MLflow without the caller inventing one. An explicit `run_name=` (YAML or ctor) is preserved verbatim. `generate_run_name(prefix=…, postfix=…, separator=…)` is the single helper (empty prefix/postfix are skipped — no leading/trailing/double separators); use it (not a bespoke timestamp/uuid) anywhere a default run/experiment id is needed. `coolname` is a marainer dependency.
- **Task Subclasses Own Dimension Resolution (the base stays task-agnostic):** `LightningTrainer.run()` / `LightningEvaluator.run()` flow the model + metrics **plainly** (`self.model = flow(self.model)`, `self.train_metrics = flow(self.train_metrics)`, …) — the base names NO task dimension and does no dataset introspection. A task subclass that needs a dimension (e.g. classification's `num_classes`) resolves it and flows the model + metrics WITH it in an explicit `initialize()` called at the top of its own `run()`, BEFORE `super().run()`; the base's later `flow()` is then idempotent on the now-live instance. Reference: `sonair.LightningClassificationTrainer.initialize()` (derives `num_classes` via `sampleflux.num_classes(train_set)` — data-driven, it sizes a fresh model) and `sonair.LightningClassificationEvaluator.initialize()` (reads `num_classes` off the **trained model**, NOT the eval dataset, which may be a subset). The old generic `marainer.dimensions` layer (`needs_derivation` / `collect_derived_dimensions` / `flow_node_with_dims`) and the dataset `derived_dimensions()` hook were **removed** — flow the classes into instances directly. Do NOT add `num_classes` (or any task dimension) to the base trainer signature or step functions; a task without an `initialize()` simply needs its model/metrics explicitly configured.
- **SampleFlux Lineage:** All training data flows through `sampleflux.Sample(input, target, metadata)`. Never bypass metadata — full sample-to-prediction traceability is mandatory for sinks and downstream analysis.
- **Loggers Belong Under `lightning.logger:`:** PyTorch Lightning's only logger-attachment path is `Trainer(logger=…)`, which maps to `lightning.logger:` in YAML — NOT a top-level `loggers:` key on the marainer trainer (no such kwarg exists; any field there is silently ignored and Lightning falls back to its default `./lightning_logs/`). When adding loggers to a YAML, put them under the `lightning:` block. The contract is pinned by `tests/test_loggers.py::TestYamlLoggers::test_yaml_loggers_reach_lightning_trainer`.
- **Predictions Sinks:** `Evaluator.predictions_sink` consumes per-sample dicts. Detection/classification/segmentation models MUST emit a per-sample mapping (not a batched tensor) when used in predict mode.
- **System Metrics On by Default:** `LightningTrainer.run()` (and its `raidar_ultralytics.UltralyticsTrainer` sibling) call `marainer.system_metrics.activate_for_lightning` / `enable_mlflow_system_metrics` automatically when an MLflow run is wired. On Apple-Silicon hosts the activation also appends an `MPSMetricsCallback` that samples nine `system/mps_*` scalars in a daemon thread (default 10 s cadence, overridable via `MLFLOW_SYSTEM_METRICS_SAMPLING_INTERVAL` env var or the `sample_interval_s` kwarg) and pushes them straight to MLflow via `MlflowClient.log_metric`. Three of the scalars come from `torch.mps` (per-process memory); six come from the `apple-gpu` package's `IOAccelerator.PerformanceStatistics` read (device / renderer / tiler utilisation + system-level memory; no sudo). Pass `log_system_metrics=false` to opt out per-trainer; flip `MLFLOW_ENABLE_SYSTEM_METRICS_LOGGING=false` in `.env` to suppress workspace-wide.
- **Default ModelCheckpoint + YAML Logging On by Default:** `LightningTrainer.run()` auto-injects a `ModelCheckpoint` into `lightning.callbacks` BEFORE `flow(self.lightning)` whenever none is already present and `enable_checkpointing` is not `False`. The default is `save_last=True` + `save_top_k=1`; the monitored key resolves in this order: first key in `val_metrics.metrics` (with `mode` from `higher_is_better`) → `val/loss` (`mode=min`) when a `val_set` is wired → `train/loss` (`mode=min`) otherwise. After flow, the full YAML include tree from `liquifai.context.get_context().included_paths` is logged as an artifact to every wired Lightning logger (MLflow → `experiment.log_artifact(... "config")`; TensorBoard / CSV → file copy into `<log_dir>/config/`). Loggers are the stock `pytorch_lightning.loggers.*` classes wired under `lightning.logger:` — there is no marainer-specific logger subclass.

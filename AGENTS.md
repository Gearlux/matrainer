# Marainer Mandates

## Current state

A PURE experiment-**tracking** library (v0.2.0) with a light core install: `marainer.tracking` (the `Tracker` ABC + four lazily-importing backends, provenance, system metrics), the optional per-framework helpers `marainer.lightning` / `.tensorflow`, plus `marainer.checkpoints`, `.run_names`, and `marainer.torch` (`load_lightning_checkpoint` + the Lightning-free metric helpers, which moved down from `marainer.lightning` on 2026-08-01). No training loop, no CLI, **no data plumbing** — runs go through `recordstream run`; the runnable protocol, workflow combinators and `DatasetProcessor` live in recordstream, and so (since 2026-07-29) do the dataset normalizer, the prediction contracts and the predictions sink (see the mandate below). Data is the recordstream **record** (a plain dict of typed values); marainer never reshapes it.

- **The Run Manifest Is The UNION; A Native Slot Is A PROJECTION (`marainer.tracking.manifest`, 2026-08-01):** SHIPS end to end — the accumulator, the capture sources (`capture_environment` / `capture_code` / `capture_config`, backed by `tracking/provenance.py`), `Tracker.log_manifest`, the MLflow + TensorBoard native projections, and `log_run_context` as the ONE orchestration entry (it fills a manifest, projects it, and RETURNS it; `capture_log_file(trackers, manifest=…, status=…)` finishes it). **`capture_log_file` ALSO ends the run on every tracker (`Tracker.finalize(status)`, 2026-08-02) — and that belongs here, not in each consumer.** Nothing called `finalize` anywhere until a real MLflow sweep showed eleven of thirteen FINISHED runs as `RUNNING` with no end time: the same run said `success` on disk and in-flight in the UI, and no backend could report a duration. The two that looked right did so BY ACCIDENT — a Lightning consumer adapts its trackers into `pl.Logger`s and Lightning finalizes those itself. This function already stated the terminal status and already looped the trackers, so putting it here fixed all eight consumers at once; a per-consumer call would be eight chances to forget and eight places for the tracker's status to disagree with the manifest's. **Finalizing is LAST**, after the artifact and manifest pushes, because a backend with a run lifecycle stops accepting writes once closed — MLflow tolerates a late write (measured: the metric lands, status stays `FINISHED`), `WandbTracker` does not (its `finish()` drops the run handle, so the next access starts a NEW run), which is what the `finalize=False` escape hatch is for. Pins: the ordering + escape-hatch tests in `tests/tracking/test_provenance.py`, and consumer-side `test_the_terminal_call_is_the_one_that_ends_the_run`, which forbids a backend calling `finalize` for itself. `manifest.py` + `provenance.py` are both at 100% coverage. Contract in `docs/architecture.md` record 3. **The base `log_manifest` projects `params` via `log_hyperparams`** — the one native slot EVERY backend has, so it belongs in the default, not in each override; an override calls `super()` FIRST and then adds its own slots (rule 2 is "also", never "instead"). **`primary_code()` may return `None` ON PURPOSE:** a backend with ONE source-commit field cannot hold the manifest's LIST, so the narrowing is ordered (repo containing the cwd -> repo containing the entry script -> a lone record) and declines when none applies. Do NOT "fix" that by falling back to `entries[0]` — it previously did, and a real MLflow run got an unrelated workspace package's commit stamped as `mlflow.source.git.commit` purely because it sorted first (found by running it, not by a test). An empty native field sends the reader to the manifest; a wrong one looks exactly like a right one. Three implementation rules the capture side encodes and that must not be undone: (a) **`capture_code` returns a LIST** — `code_state()` discovers editable installs via PEP 610 `direct_url.json` and dedups by git toplevel, because a run's behaviour is set by every editable package on `sys.path`, not by the CWD repo `get_git_commit_hash()` sees; (b) **`environment_snapshot` REDACTS** any name matching `SECRET_MARKERS` (TOKEN/KEY/SECRET/PASSWORD/AUTH/…) — the manifest is an uploaded artifact, so a captured `WANDB_API_KEY` would be a secret published to every backend; keep the NAME (that a token was set is provenance), drop the value; (c) **`accelerator_state` reads `sys.modules.get("torch")`, never `import torch`** — importing a framework to ask what device it uses would make a light tracking call pay a multi-second import, or pull in a framework the process deliberately did not choose. `config_params` is now the ONE hyperparameter derivation (it keeps scalars + all-scalar lists, and drops objects because a repr carries a memory address that would make identical runs diff); a consumer re-deriving its own is the divergence this ended. The three contract rules, in order of how easily they get broken: (1) **every static fact lands in the manifest unconditionally**; (2) a backend with a native home for a fact ALSO writes it there; (3) **no fact is ever native-only** — the moment one is, the same run tracked two ways stops being comparable and moving between backends silently loses fields, which is the entire reason this exists. **Three additions on 2026-08-02, all under the SAME rules:** (a) **`command.line`** — the invocation as a shell snippet a person can PASTE to rerun, `cd <cwd>` included so a relatively-referenced config resolves. It exists because `argv` alone CANNOT be pasted back: the workspace's runner is launched with `-m`, whose `argv[0]` is the module's FILE path (`.../recordstream/cli.py`) and does not re-execute — so `command_line()` detects the launch shape (`__main__.__spec__` set -> `-m <module>` with a trailing `.__main__` stripped; a non-`.py` executable -> pasted verbatim, since a console script carries its own shebang; else the interpreter in front) and `shlex.join`s it against the absolute `sys.executable`. Both fields STAY — `argv` is what `primary_code()` parses — and `line` is OMITTED, never guessed, for `argv[0] in UNREPRODUCIBLE_ARGV0` (`""`/`"-"`/`"-c"`, where the code never reaches `sys.argv`). Verified by pasting a real manifest's line from `/` and watching the training rerun. (b) **`capture_packages()`** -> `environment/requirements.txt` + `env.packages = {path, sha256, count, tool}`. `uv pip freeze --python <sys.executable>` when `uv` is on PATH, else `pip freeze`: MEASURED 0.063 s vs 0.963 s on 730 distributions, and this runs on every tracked run — `--python` pins the environment so cwd and activation are irrelevant. Nothing is lost by preferring uv: the two disagree only on how they spell an editable install, and pip's frozen commit cannot express `dirty`, which `code_state()` already records. Every failure (no pip, non-zero exit, timeout) is a debug log + `None`. (c) **`capture_datasets(runnable)`** -> the `datasets` section, which was EMPTY on every manifest ever written because `record_dataset` had zero callers workspace-wide. It walks the runnable with **`configured_slots`**, a deliberately DIFFERENT walk from `config_params`' — that one flattens to leaf SCALARS (a hyperparameter is a value), this one needs the OBJECTS (what identifies a dataset is a source) — and asks each via recordstream's `dataset_uri`/`dataset_url`, which follow `.source` wrappers themselves. **`kind`/`name`/`split` are DERIVED from the URI** (scheme / path / `split` param), so marainer learns nothing source-specific and a new source type needs no change here; entries dedup by URI keeping the FIRST (outermost) slot, which is why recordstream propagates a view's URI verbatim. All three are called from `log_run_context`, NOT by each consumer — the same argument that put `Tracker.finalize` in `capture_log_file`: ten runnables already reach this function, and a per-consumer call is ten chances to forget. (d) **`capture_models(runnable)`** -> the `models` section, empty for the same reason `datasets` was (`record_model` had zero callers). It reuses the SAME `configured_slots` walk and the same URI-derived `kind`/`name`, but the PROTOCOL it reads has a deliberately different SHAPE, and that asymmetry must not be "tidied away": a dataset source exposes two plain strings because it reads ONE dataset, while a model wrapper exposes a LIST (`marainer.uri.model_refs`) because it COMPOSES artifacts — a backbone fine-tuned from a checkpoint used two, and each `ModelRef` carries the `role` it played (`pretrained` = from outside the run, `checkpoint` = from a previous run of ours). A pipeline composing several models is the same shape one level up, which is why plural was chosen over "checkpoint wins". **`marainer/uri.py` is TOP-LEVEL and stdlib-only** for the `metric_slots` reason — nine model wrappers across four consumer projects import it, several on deliberately framework-free backends — and NOT re-exported from the package root, which is the tracking surface. `hf_model_ref` is the ONE spelling of `hf://models/<id>` shared by the five wrappers that resolve to the Hub (mirroring recordstream's `hf://datasets/`), so they cannot drift into three formats that stop comparing equal for the same weights. **TWO invariants that are easy to undo and were both found by RUNNING it:** (1) **reporting an EMPTY list is an answer** — the walk stops at any object that implements the protocol, because falling through follows `.model`, which on `HuggingFaceModel` / `KerasModel` is a property that BUILDS; the guard is `refs is not None`, never truthiness (caught by a consumer test: a `pretrained=False` model raised *"num_classes is not set"* from inside a provenance read). (2) **asking never builds** — `_materialize` flows a deferred `Fluid` marker ONLY, never a live object, because `flow()` on a live object runs `solidify()`, which downloads weights and raises when the runnable has not injected `num_classes` yet. recordstream's `dataset_uri` was narrowed the same way in the same change. **(3) A FRAMEWORK-HELD child is still a slot — `configured_slots` reads `_modules`, not only public `__dict__` keys (2026-08-03).** `torch.nn.Module.__setattr__` diverts every Module-valued assignment into `self._modules`, keyed by the attribute name the caller used, so `self.model = TimmModel(...)` leaves `model` ABSENT from `__dict__` entirely — and the walk's "public attributes only" rule then made the model of EVERY torch-based runnable invisible. The manifest wrote `models: []` while `datasets` (a plain attribute, so still in `__dict__`) filled correctly: a complete-looking run, a green suite, and not one weight named. Found by READING A REAL RUN'S MANIFEST, which is the only place it was visible — every unit test passed, because a hand-built fake stores its attributes normally. `_CHILD_REGISTRIES` is the narrow exception to the underscore rule and is justified by one property: its KEYS are the public names the caller assigned, so nothing private is exposed. It is detected STRUCTURALLY (a `_modules` attribute that is a Mapping), never by an `isinstance` against `torch.nn.Module` — the same reason `accelerator_state` reads `sys.modules` — and a real public attribute always wins over a same-named child, so no slot is yielded twice. Pins: the framework-held-child group in `tests/tracking/test_provenance.py`, whose fake REPRODUCES the diversion rather than storing attributes normally (a fake that does not is exactly what let this ship). Per-wrapper spellings: timm resolves the exact tagged repo via `timm.get_pretrained_cfg(name).hf_hub_id` (static registry — 0.0000 s, offline, `None` for an unknown name), a Hub id is itself, and a zoo with no repository page (`keras://applications/…`, `smp://<arch>/<encoder>?weights=…`, `rfdetr://<variant>`, `ultralytics://yolo26n`) names the registry + entry and reports NO url rather than inventing one. (e) **PORTABLE PATHS — `$PROJECT_ROOT` / `$DATA_ROOT` / `$MODEL_ROOT` (`PORTABLE_ROOT_VARS`):** where one of those vars is SET, every absolute path under it is recorded as `$NAME/...`, so a manifest read on a machine that keeps its code/data/models elsewhere still points at the right things. **It is applied ONCE over the WHOLE document — in `to_dict()` AND `section()`, never at a capture site** — so a section added later is portable without anyone remembering, and so what is WRITTEN and what a native projection READS cannot disagree (a hosted backend's dataset field holding an absolute path beside a portable artifact is exactly the drift record 3 exists to prevent). **`os.path.expandvars` is the EXACT INVERSE** (pinned by `test_expandvars_is_the_exact_inverse`) — that is what makes contracting a whole document safe rather than lossy, and `contract_roots` is idempotent so a double application is harmless. **`env.roots` is the ONE skipped subtree (`PORTABLE_SKIP_KEYS`)**: it is the expansion table, and contracting a definition into a reference to itself would destroy the only record of what the root WAS — a reader without the vars set has nothing else to resolve from. Matching is on a path BOUNDARY (`/store` must not swallow `/storefront`) and the LONGEST root wins (a `MODEL_ROOT` nested inside `DATA_ROOT` resolves to the nearer one) — both pinned. **The quoting of `command.line` changed WITH this and the two cannot be separated:** `shlex.quote` wraps a `$` in SINGLE quotes, where it is a literal dollar sign — so the contracted line would have looked right and pointed at a directory that does not exist. `_quote` double-quotes any word carrying a variable (the shell expands inside those, and the expansion may itself contain a space, so bare is not an option either). Set no root and NOTHING changes — contraction is opt-in by configuration. (f) **A LOCAL artifact carries `size` + SHA-256 `digest` (`local_file_facts`, 2026-08-03)** — the question `record_model`/`record_dataset`'s long-unfilled `digest` field exists for: is the checkpoint still on disk the one the run loaded? Applied to `file:` URIs in BOTH `configured_models` and `configured_datasets`. THREE deliberate non-answers: a REMOTE reference gets neither (identified by URI + revision; fetching gigabytes to fingerprint it would be absurd), a DIRECTORY gets neither (a SavedModel / imagefolder has no single content hash, and walking one to invent a composite is unbounded work at every run start), and a file above `MAX_DIGEST_BYTES` (2 GiB) keeps its `size` and skips the digest. `size` is free (one `stat`) and recorded ALWAYS, so an over-cap file is still distinguishable. Measured 1790 MB/s, so the default cap costs at most ~1.2 s. The facts are computed from the RAW absolute URI in `configured_*`, BEFORE the manifest contracts it — a `$MODEL_ROOT` path would stat nothing. **A referenced artifact must TRAVEL with the manifest:** `RunManifest.artifacts()` lists the side files (`config/final.yaml`, `environment/requirements.txt`) and the base `log_manifest` uploads them, skipping any already inside `log_dir`. This closed a live gap — `config/final.yaml` had been written since the manifest landed and NEVER uploaded, invisible on a file-backed backend (where it happens to sit in the right tree) and simply missing on every remote-only one, which is rule 3 broken by omission. `_write_artifact(relative, text)` is the ONE side-artifact write both callers use; do not re-hand-roll it. Serialization is `manifest.yaml` **and** `manifest.json` from ONE atomic write (temp + `os.replace`) after EVERY mutation — crash-safety is a WRITE POLICY, not a shutdown hook, so an interrupted run leaves a complete record and the `atexit`/`SIGINT`/`SIGTERM` handlers only stamp the terminal `status`. Never buffer until run end. YAML is `yaml.safe_dump(..., sort_keys=False)` — plain and TAG-FREE: confluid's dump emits `!class:` / `!ref:` / `!clone:` that only its own resolver reads, so the resolved config goes to its OWN `config/final.yaml` artifact referenced by digest, never inlined (the same "we log it, we don't re-own its FORMAT" rule as `marainer.artifacts`). `pyyaml>=6.0` is a DECLARED core dep (it was previously reachable only transitively through confluid — a module that imports a package must depend on it); do not drop it back. Code provenance becomes a LIST (one record per editable distribution), because a run's behaviour is set by every package on `sys.path`, not by the CWD repo `get_git_commit_hash()` happens to see. The only new `Tracker` method is `log_manifest(manifest)`, defaulting to serialize + `log_artifact` — no wrapper layer over `Tracker` (that rule still holds).
- **Dataset + Model Lineage Reach The NATIVE Slots Too (`_project_datasets` / `_project_models` / `_project_inputs`, 2026-08-03):** with `datasets` and `models` finally populated, MLflow and W&B get them in their OWN lineage surfaces — rule 2 ("also", never "instead"): the union artifact still carries everything. **MLflow:** datasets are `DatasetInput`s and models are `LoggedModelInput`s, which need a logged-model ID, so `create_logged_model` makes the entity from METADATA ALONE first — no weights uploaded, the Model Registry untouched, every manifest field riding along as a tag. **W&B:** both sections become typed `Artifact`s marked `use_artifact` (that IS the lineage graph), with `add_reference` when the URI names a location W&B can address — a reference records WHERE the bytes live rather than uploading them. **THREE library behaviours that read as bugs if you do not know them, all MEASURED, all pinned:** (1) **MLflow does NOT dedup a logged model** the way it dedups a dataset input by digest, and `log_manifest` runs at least TWICE per run — so `MlflowTracker._logged_models` (URI -> model id) is what keeps every model from appearing twice; deleting it looks harmless and silently doubles every run's lineage. (2) **Both libraries restrict entity NAMES to sets that exclude every separator a real identifier uses** — MLflow rejects `/ : . %` and quotes outright (`Invalid model name`), W&B allows only alphanumerics/dashes/underscores/dots, so `timm/resnet50.a1_in1k` is refused by BOTH; the name is a sanitised LABEL (`_logged_model_name` / `_artifact_name`) and the exact identifier lives in the tags/metadata. (3) **`wandb.Artifact.add_reference` IS NOT FATAL and gets its OWN `try` (`_add_reference`, 2026-08-03).** It VALIDATES eagerly — a `file://` path not on this disk raises `ValueError`, and an `http(s)://` URI is FETCHED (a 404 raises `HTTPError`) — and it used to share the caller's `try` with `use_artifact`, so a reference failure skipped the registration too and the entry VANISHED from the lineage graph rather than degrading to the metadata-only form a zoo URI already gets. The artifact is the record; the reference is only an optimisation on top of it. **The URI is `expandvars`-ed before referencing, and that half is not optional:** the manifest is PORTABLE, so with `MODEL_ROOT` set a checkpoint's URI is stored as `file://$MODEL_ROOT/last.ckpt` — deliberately not a path anywhere — meaning a checkpoint reference could NEVER resolve on a machine that has the roots configured, which is every machine that sets them. `expandvars` is the documented exact inverse of `contract_roots`. Found by driving the REAL wandb library rather than the fake, which accepted any path — so the fake now enforces the must-exist rule too, since a fake that does not is what let this ship. **`wandb.Artifact.add_reference` REFUSES an unknown scheme** (*"You must pass name=… when tracking references with unknown schemes"*), so a zoo URI (`hf://`, `smp://`, `ultralytics://`) is metadata-only and only `REFERENCEABLE_SCHEMES` become references. Also: `model_type` reads `kind` **or** `source`, because `capture_models` writes the first and the manual `record_model` takes the second. **Reading it back, `client.get_run(run_id).inputs.model_inputs` is the query that works — `search_runs` returns runs whose `model_inputs` is EMPTY while `dataset_inputs` is populated**, so verifying lineage that way shows datasets landing and models silently missing, which is a convincing-looking bug in code that is doing the right thing (it cost a full debugging pass; the docstring says so too). Verified against a REAL sqlite MLflow store (two `log_manifest` calls -> 1 dataset input + 2 model inputs, not 2 and 4) and the REAL wandb library's validators, not only the fakes. Pins: the model-lineage group in `tests/tracking/test_mlflow_backend.py` and the lineage group in `tests/tracking/test_wandb_backend.py` — whose fakes ENFORCE the real name rule and the real `add_reference` scheme rule, so a dropped sanitiser fails there instead of only in production.
- **`log_text` Is The THIRD Content Channel, And Its Default Is REAL WORK (`Tracker.log_text`, 2026-08-01):** `log_metrics` takes numbers and `log_figure` takes images; a run value that is NEITHER — a confusion matrix rendered by `render_matrix_as_table`, a classification report, a diff — had no channel at all, so a consumer computing one could only put it in the log and a tracked run recorded the scalars beside it as though that were the whole result. `log_text(name, text, step=None)` is that channel. **Unlike `log_figure`, whose base implementation is a debug-logged skip, this default DOES the work** — text is trivially serializable, so the ABC writes a `.md` file under the backend's own `log_dir` (or, for a remote-only backend with no tree, into `save_dir` followed by `log_artifact(..., artifact_dir="text")`) and a caller never has to ask whether THIS backend can hold a table. The artifact call is skipped when the file is already inside `log_dir` — the same rule `log_manifest` applies, and without it a file-backed backend writes the same text twice into one tree. **A backend with a native text channel overrides and uses it INSTEAD, which is the OPPOSITE of the `log_manifest` rule and deliberately so:** there the artifact is a UNION guarantee that keeps two differently-tracked runs comparable, so a native slot is written "also, never instead"; here the text IS the payload and one durable home per backend is the entire requirement, so a second copy is just a second copy. The natives: MLflow `client.log_text` (writes the artifact itself), TensorBoard `add_text` (the Text tab, `step` driving the slider — durable in the event file, so the `.md` twin would add nothing), Aim `aim.Text` tracked as a sequence, and ClearML **`upload_artifact`, NOT `report_text`** (its text primitive writes to the task's CONSOLE stream, where a per-epoch table is interleaved with everything the process printed and cannot be compared between tasks). W&B deliberately does NOT override — it has no text primitive (`wandb.Html` means escaping the caller's text into markup, a `wandb.Table` is a dataframe under another name) while its run directory IS its upload channel, so the inherited file is synced for free and stays readable as itself. **`step` is part of the FILENAME (`text_file_stem`, shared so every backend files the same value under the same name), never a version of one file** — a value logged once an epoch would otherwise keep only its last value on any backend whose channel has no step axis. `render_matrix_as_table` gained a BLANK line after its title in the same change, and that is functional rather than cosmetic: it is now handed to markdown renderers (the Text tab, MLflow's `.md` preview) that need one to see a table instead of a run-on paragraph. **`render_matrix_as_figure` is its `log_figure` twin (2026-08-02), and the two are a deliberate PAIR rather than one superseding the other:** the table needs `tabulate`, is readable in a plain log and costs nothing, so it is what a consumer sends by default; the heatmap needs matplotlib (the new `[plot]` extra) on every eval epoch and is the only form still readable once there are many classes, so it is opt-in. **It builds `matplotlib.figure.Figure` DIRECTLY, never `pyplot.subplots`** — a pyplot figure is registered in a process-global manager and stays alive until someone calls `pyplot.close`, so a value rendered once an epoch leaks a figure per epoch in a caller that has no reason to know pyplot has global state; a bare `Figure` is owned by its reference and every backend's `log_figure` accepts it (verified for the `savefig`, `add_figure`, `log_figure` and `report_matplotlib_figure` paths). Cell annotations stop past 25 classes — unreadable by then, and the cost grows with N². Both renderers share `_as_rows`, which is where the `detach().cpu().tolist()` / `tolist()` / already-a-list ladder lives. Pins: the `log_text` group in `tests/tracking/test_base.py` (default file, remote upload, per-step files, group fan-out) + one per native backend + `tests/tracking/test_render.py` (the renderer had shipped with NO tests until it acquired a consumer; the pyplot-registration check is the one that would catch a "simplification" to `pyplot.subplots`).
- **A PER-CLASS VECTOR Gets Its OWN Renderers, Not The Matrix Ones — `per_class_vectors` / `render_vector_as_table` / `render_vector_as_figure` (2026-08-03):** `scalar_metrics` drops two shapes, not one: a square `N×N` confusion matrix AND a length-`C` per-class vector (what `average=None` produces). The matrix pair shipped 2026-08-02; the vector pair completes the set, and it is a SEPARATE pair rather than a widening of the first because a per-class metric is not a degenerate matrix — it has ONE axis of meaning, its values share a scale (they are all fractions), and what a reader wants from it is a RANKING. So the table is sorted **worst-class-first** and the figure is a horizontal BAR CHART with the mean as a dashed reference line, where the matrix renderers give class-ordered rows and a heatmap. A `1xC` heatmap strip would answer "which class is the model worst at" by making the reader decode colours against a colorbar. **`per_class_vectors` is the SELECTION rule and it matches by SHAPE, never by metric NAME** (a flat numeric sequence of length >= 2): a runnable emits scalars, vectors and matrices in ONE `compute()` mapping with no knowledge of which is which, so a name-based rule would need every consumer to agree on a convention nothing enforces. Scalars fall through (a scalar belongs in `log_dict`) and so do matrices, which is what lets the SAME mapping be handed to both selection rules with each taking only its own. **It lives HERE, beside its renderers, rather than upstream beside recordstream's `confusion_matrices_payload`** — that one exists because a confusion matrix feeds a GUI VIEWER and needs a normalized payload; a per-class vector feeds no viewer and needs no payload, so its only consumers are the two renderers below it and a selection rule is best read beside what selects for it. Two implementation details are load-bearing and both have the same shape as the matrix pair's: the figure is built through `matplotlib.figure.Figure` DIRECTLY (a pyplot figure is registered in a process-global manager and leaks one per eval epoch), and the table passes FLOATS to `tabulate` with `floatfmt=".4f"` rather than pre-formatted strings — tabulate PARSES a numeric-looking string and reformats it, so `f"{v:.4f}"` would be silently re-rounded and the column would not have the precision it appears to ask for. A length mismatch between `class_names` and the vector falls back to INDEX labels rather than dropping the value, because it usually means a metric with its own axis (a per-threshold curve) rather than a bug worth hiding a value over. Pins: `tests/tracking/test_render_vector.py` (22 — the selection rule in both directions, the worst-first sort in table AND figure, the pyplot-registration check, the precision one).
- **Backends Are Separately Installable — Tolerate / Declare / Select (2026-08-01, ALL THREE SHIP):** rationale in `docs/architecture.md` record 4. **(1) Tolerate:** each backend imports its library lazily INSIDE its methods via `require(module, extra)`, so `import marainer.tracking` pulls in none of them and a missing library is one actionable `pip install marainer[<extra>]` error — pinned by `tests/test_light_import.py`. **(2) Declare:** `pyproject.toml`'s `[tool.aisland] trackers = [...]`, a table **SIBLING** to `frameworks` — never folded into it, because what a machine trains WITH and where its results GO are independent axes, and merging them installs a tracking client because someone picked a training engine. **(3) Select:** the workspace environment manager's `aisland tracker` (the committed `trackers` key of the workspace `config.toml` + a per-machine git-config override that must never reach a tracked artifact). **Backends are DISCOVERED, never listed (`tracking/__init__.py`):** `discover_backends()` scans this package for `*_backend.py` and collects `Tracker` subclasses; a module-level `__getattr__` (PEP 562) resolves them, in BOTH `marainer.tracking` and `marainer`. Do NOT reintroduce a fixed import list or a hand-written `__all__` entry per backend — that was two places to forget, and an out-of-tree backend could appear in neither (it is discovered through the `confluid.configurables` entry point instead). Adding a backend is ONE new file; `tests/test_discovery.py` proves it by writing a real module into the package directory and resolving it. The scan importing every backend module is safe and intentional — they import their libraries lazily, so it costs nothing and the light-import test pins that. In-tree selection criterion is **free and self-hostable** (CSV/MLflow/TensorBoard/**Aim**/**ClearML** all shipped; W&B stays supported but is not what a fresh checkout is steered toward) — the user-facing survey lives in `README.md` § "Choosing a backend"; keep the RULE here and the SURVEY there.
- **`ClearMLTracker` Must Not Change The Process It Measures (`tracking/clearml_backend.py`, 2026-08-01):** `Task.init` is called with **`auto_connect_frameworks=False`** — ClearML otherwise monkey-patches torch, matplotlib and argparse to capture them implicitly, and a tracking library silently altering how the measured process behaves is exactly what marainer must never do. Do not "enable the nice auto-capture". Three more, all measured against clearml 2.1: **`offline=True` is process-wide and effectively one-way** (`Task.set_offline(False)` validates the ClearML config and raises `MissingConfigError` on an unconfigured machine — which is how the integration test first failed, in its own CLEANUP; the test now restores `CLEARML_OFFLINE_MODE` through `monkeypatch` instead); **`log_metrics` splits `train/loss` into `report_scalar(title="train", series="loss")`**, because that is how ClearML's UI groups related curves into one graph; and `set_tags` resolves the task BEFORE merging into `self.tags`, the same double-add trap as the Aim backend. **`InputModel.import_model` is given ONLY an addressable URI (`ADDRESSABLE_SCHEMES`, 2026-08-03).** ClearML REWRITES an unknown scheme rather than rejecting it: `StorageHelper.conform_url` treats it as a relative path and resolves it against the CWD, so `hf://models/timm/x` was registered with `url=file://<cwd>/hf:/models/timm/x` — a local file that does not exist, pointing wherever the run happened to start. Every zoo scheme this workspace mints (`hf`/`smp`/`keras`/`ultralytics`/`rfdetr`) hit it, and a broken link in the Models tab is worse than no link because it looks like a right answer — the same rule as `primary_code()` declining rather than guessing. Passthrough was MEASURED per scheme against a LIVE server (`file`/`http`/`https`/`s3`/`gs` conform unchanged; `azure` raises without credentials, which the caller's `except` reports — a loud miss, not a silent rewrite). An unaddressable model is not lost: it stays in the `models` hyperparameter section, which is why that section is kept BESIDE this registration rather than replaced by it. Found only by starting the server — the fake accepted any URL, so the two tests that asserted the zoo model WAS imported had been pinning the defect. The manifest projection uses `connect_configuration` (Configuration tab, diffable between tasks) plus `connect(..., name="datasets"/"models")` (comparable across runs) — both ADDITIONAL to the artifact, per record 3 rule 2. **`_project_input_models` adds a THIRD, SERVER-ONLY slot (2026-08-03):** `InputModel.import_model(weights_url=…)` registers each model artifact as a first-class model the task links to (Models tab + lineage graph), importing BY URL so no weights are uploaded. **It needs a server** — measured against clearml 2.1, offline it dies with `AttributeError: 'NoneType' object has no attribute 'response'` — so `self.offline or Task.is_offline()` skips it ONCE with a debug note instead of failing per model per `log_manifest`, and the flat hyperparameter section STAYS rather than being replaced: offline, it is the only projection there is. Models are memoised per URI (`_input_models`) because `log_manifest` runs at least twice per run, and **the memo is written the moment `import_model` SUCCEEDS, before `task.connect`** — the registration is what would duplicate, so a failure to LINK must not send the next pass back to re-register weights the server already has (a real ordering bug, caught by the dedup test). Pins: the model-lineage group in `tests/tracking/test_clearml_backend.py`, whose fake `connect` accepts an OBJECT as the real one does.
- **`AimTracker` Maps Onto Aim's Model, Not Ours (`tracking/aim_backend.py`, 2026-08-01):** three things measured against aim 3.29 that read like bugs if you do not know them. (a) **`log_hyperparams` must MERGE by hand** — Aim replaces `run["hparams"]` wholesale, so the accumulated dict is kept on the tracker and re-assigned; marainer's contract is that repeated calls add. (b) **`set_tags` resolves the run BEFORE merging into `self.tags`** — creating the run applies whatever `self.tags` already holds, so merging first made every tag land TWICE (caught by a test, fixed by ordering; `tests/test_aim_backend.py::test_set_tags_before_the_run_exists_does_not_double_add`). (c) **`log_dir` returns `None` on purpose** — `Tracker.log_manifest` skips uploading a file already inside `log_dir`, and a file merely SITTING in Aim's directory is not registered with Aim, so returning a directory would silently stop the manifest ever reaching it. Also: `log_artifact` needs `set_artifacts_uri` first (Aim raises otherwise) and names artifacts `<dir>/<file>` so `config/x.yaml` and `logs/x.yaml` cannot collide; `capture_terminal_logs` defaults to **False** against Aim's own default, because loggair already writes the log `capture_log_file` uploads. **Aim's structured run values ARE its most native slot for lineage, and there is nothing richer to reach for (checked 2026-08-03):** its public surface is `Run`/`Repo` plus the sequence types (`Metric`/`Text`/`Image`/`Audio`/`Distribution`/`Figure`) — there is NO artifact, dataset or model entity to register into, unlike MLflow's dataset+logged-model inputs, W&B's Artifacts or ClearML's InputModel. So `run["datasets"]` / `run["models"]` is the ceiling, not a placeholder; do not add a fake registry to make the backends look symmetric. **Reading a run back is index-served:** `Repo.iter_runs()` can legitimately return nothing right after a finished run while every value is on disk (`aim up` indexes at startup) — the module docstring says so, and the integration test reindexes deliberately. Do not "fix" that.
- **A Framework Helper Requires The FRAMEWORK, Not Its Heaviest Distribution (`marainer.keras`, renamed 2026-07-30):** the Keras tracking subpackage was `marainer.tensorflow` and did `require("tensorflow.keras", "tensorflow")` — forcing a ~2GB TensorFlow install on a consumer training with **Keras 3 on the torch backend**, a framework it had deliberately not chosen. Keras 3 is STANDALONE and picks its compute backend via `KERAS_BACKEND`; `tf.keras` IS Keras 3 in TF >= 2.16, so `import keras` is the same API with none of the weight. The subpackage is now `marainer.keras`, behind a new `[keras]` extra; `[tensorflow]` becomes `marainer[keras] + tensorflow` for a consumer that genuinely wants that ENGINE. The general rule: an optional helper's extra names the API it imports, never a distribution that happens to bundle it — otherwise selecting one framework silently installs another. **The import goes THROUGH `recordstream.keras` (2026-07-30, fixing a real failure):** Keras reads `KERAS_BACKEND` at IMPORT time and its own default is `tensorflow`, which this extra deliberately does not install — so the previous `require("keras", "keras")` died with `ModuleNotFoundError: No module named 'tensorflow'` whenever the callback was the FIRST keras import in a process, and `require` then reported *"the 'keras' package is not installed"*, which fixes nothing because keras WAS installed (the real cause was only visible in the chained traceback). `recordstream.keras` owns the `os.environ.setdefault` to the first engine actually PRESENT (recordstream `AGENTS.md` → the batching mandate; rationale in its `docs/architecture.md` §10), so the call is now `require("keras", "keras", feature=…, via="recordstream.keras").keras`. **`via=` is `require`'s new "import X, but report Y as missing" parameter** — the message must name `keras`, the thing an operator installs, never the shim, which is already present and would send them after a dead end. Do NOT bare-`import keras` anywhere in marainer, and do not "simplify" the `via=` away. Pins: `tests/test_keras.py` (the no-`KERAS_BACKEND` subprocess repro, the message-names-keras check, and that `require` without `via` is unchanged).
- **Run Artifacts Live Here; Their FORMAT Does Not (`marainer.artifacts`, 2026-07-29):** `save_class_names` / `load_class_names` persist a run's label vocabulary beside its checkpoints (`CLASS_NAMES_FILE`, a fixed name so a later evaluate/predict run can FIND it knowing only the checkpoint path) and log it as a tracker artifact; `write_metrics_sidecar` writes the final scalars stamped with the run identity. **The JSON format is recordstream's** — these DELEGATE to `LabelMap.save`/`.load` and must never re-hand-roll it (three consumers each had, which is why this exists). What marainer contributes is the checkpoint-adjacency convention and the artifact logging — that is tracking, and it is why a task package should own neither. All three take a plain directory/path and are framework-neutral; turning a framework's trainer object into that directory is the framework subpackage's job (`marainer.lightning.checkpoint_dir`). Every one is a no-op on `None`, so a caller needs no guard: a run on integer labels has no vocabulary, and a framework may not know where it checkpoints. Pins: `tests/test_artifacts.py`.
- **Marainer Is a TRACKING Library — NO Training/Evaluation Code (2026-07):** Marainer contains ONLY functionality to *log and track* an ML run — parameters, git hashes, config artifacts, log files, figures, metrics values, and system metrics — for various logger libraries and various training platforms. It holds **no training loop, no `training_step`/`validation_step`/`test_step`, no trainer/evaluator class.** A class that uses `pytorch_lightning.Trainer` reads like a standard Lightning example and lives in the CONSUMER (sonair/deltaid/raidar), NOT here. The guiding invariant: *removing marainer should need only a couple of line changes in a consumer to keep it training* (losing the rich tracking, keeping loggair logging). Do NOT reintroduce a `LightningTrainer`/`LightningEvaluator`/`LightningMarainer` base class, step functions, a `run()` loop, or a marainer CLI. (This reverses the pre-2026-07 "training orchestrator" design.)
- **The `Tracker` ABC Is the Abstraction — One Backend per File, Lazily Imported (`marainer.tracking`):** `Tracker` (in `tracking/base.py`) mirrors the `pytorch_lightning.loggers.Logger` shape (`name`/`version`/`experiment`/`log_hyperparams`/`log_metrics`/`save`/`finalize`) plus the extensions `set_tags`/`log_artifact`/`log_figure`/`log_text`/`log_dir`; `TrackerGroup` fans out to a list. The four backends live one-per-file — `CsvTracker` (stdlib only, the always-available default), `MlflowTracker`, `TensorBoardTracker`, `WandbTracker` — and each imports its library **lazily inside its methods** via `marainer._imports.require(module, extra)`, so `import marainer` / `import marainer.tracking` pulls in NONE of them and a missing lib raises one clear `pip install marainer[<extra>]` error. Every Tracker is zero-arg constructible (workspace lazy-init rule): the native handle is built on first `experiment` access. The Tracker is "abstract enough" — do NOT add wrapper layers over it (an earlier `as_tracker`/`_LoggerTrackerView` machinery was removed). Backends are `@configurable`, entry-pointed `marainer-tracking`.
- **Three Optional Hookup Styles, Consumer Chooses (per framework / use case):** A standard Lightning class pulls in marainer tracking however fits — marainer offers ALL of: (1) plain **utility functions** — `marainer.tracking.provenance.log_run_context(trackers, params)` (git hash + config artifacts + params), `capture_log_file(trackers)`, and the system-metric helpers — called from the consumer's own run wrapper; (2) an optional **`pl.Callback`** — `marainer.lightning.TrackingCallback([tracker], runnable=…)` added to `pl.Trainer(callbacks=[...])`, capturing the run context on fit/test start and finishing the manifest + log file on end. **It takes `runnable=` and forwards it to `log_run_context` (2026-08-01)** — so a Lightning consumer stops hand-building a params dict — holds the returned manifest on `.manifest`, and stamps `failed` / `interrupted` from `on_exception`, because a run that RAISED must not read as a success and an unfinished manifest gets relabelled `interrupted` by the atexit hook; (3) the **`TrackerLogger`** bridge — `marainer.lightning.TrackerLogger(tracker)` passed to `pl.Trainer(logger=…)` so a marainer Tracker receives per-step metrics like any pl logger. Metrics/curves may equally stay on stock `pytorch_lightning.loggers.*` — marainer USES pl loggers, never reimplements them. Don't collapse these to one — the choice is the consumer's.
- **`marainer.lightning` Is OPTIONAL Lightning Tracking Helpers, Not a Platform (`pip install marainer[lightning]`):** Behind the `[lightning]` extra (guarded `require("pytorch_lightning", "lightning")`). Contents: `TrackingCallback`, `TrackerLogger`, the system-metric callbacks (`MlflowSystemMetricsCallback`/`MPSMetricsCallback` + `activate_for_lightning`) which drive `marainer.tracking.system` sampling for a Lightning `MLFlowLogger` run, the progress bridge (`LightningProgressCallback`/`attach_lightning_progress`, mapping Lightning's per-batch hooks onto the `recordstream.runnable.ProgressReporting` sink), `build_checkpoint_callbacks` (translates the framework-neutral policies below into `ModelCheckpoint`s), and the metric utilities `build_metric_collection` / `coerce_metric_value` / `scalar_metrics` / `MetricPreset` — RE-EXPORTED from `marainer.torch.metrics`, where they moved on 2026-08-01 because they never needed Lightning (see the `marainer.torch` mandate below). NO training-loop class. `marainer.keras` mirrors this with `keras_tracking_callback`, which took `runnable=` on 2026-08-01 for the same reason `TrackingCallback` did — it forwards to `log_run_context`, holds the manifest, and finishes it on train end.
- **`marainer.torch` = torch-only, Lightning-free TRACKING helpers (`pip install marainer[torch]`):** `load_lightning_checkpoint` (loads Lightning `.ckpt` / Ultralytics `.pt` / plain state-dict; strips the Lightning `model.` prefix; auto-retargets to a named child) — reading back what a tracked run wrote, which is tracking's business — plus, since 2026-08-01, **`marainer/torch/metrics.py`** (`build_metric_collection` / `coerce_metric_value` / `scalar_metrics` / `MetricPreset`). It stays outside `marainer.lightning` so a non-Lightning platform (an Ultralytics trainer, a bare-torch training loop) uses it without pulling `pytorch_lightning`. Do NOT grow this subpackage back into a torch-utilities grab bag: if a helper is about the DATA, it belongs in recordstream; if it is about a FRAMEWORK's training convention, it belongs in the consuming runnable. **The metric move is that rule APPLIED, not an exception to it** — the same correction as `marainer.tensorflow` -> `marainer.keras`: those four helpers import confluid, torch and torchmetrics and NOTHING else, so living under `marainer.lightning` described their first consumer rather than their dependencies. It was found by a consumer that trains on plain torch with no `Trainer`: importing them from the old home ran `marainer/lightning/__init__.py`'s `require("pytorch_lightning")` as a side effect, so a deliberately Lightning-free backend could not use them (measured — `import marainer.lightning.metrics` left `pytorch_lightning` in `sys.modules`; `import marainer.torch` now does not). `torchmetrics` moved from the `[lightning]` extra to `[torch]` with them, and `marainer.lightning` RE-EXPORTS all four so its public surface is unchanged (`from marainer.lightning import scalar_metrics` still works — raidar's detector does exactly that). Pins: `tests/test_metrics.py`. **`marainer/torch/device.py` joined them on 2026-08-02 under the SAME rule** — `resolve_device(choice)` + the closed `Device` Literal (`auto`/`cpu`/`cuda`/`mps`). A `Trainer` picks an accelerator for you; a hand-written loop has to pick one itself, and every such loop picks identically (CUDA -> MPS -> CPU), so it is a torch-platform helper rather than one loop's private function. An EXPLICIT choice is taken at its word — no availability probe runs — so an operator comparing a CPU run against a GPU one cannot silently get a fallback that makes the benchmark meaningless, and `device: cuda` on a machine without it gets torch's own error. **Deliberately DISTINCT from `tracking/provenance.py::accelerator_state`, which must not be merged with it:** that one REPORTS what the process is already running on and reads `sys.modules.get("torch")` precisely so a light tracking call never pays for a framework import, while this one DECIDES where a run will execute and imports torch outright. Merging them would either force an import into the tracking path or make a device choice silently skippable. Pins: `tests/test_device.py`.
- **What Moved DOWN To recordstream, And The Rule It Encodes (2026-07-29):** four things left marainer in one pass, all for the same reason — *a package must not own a contract whose only reader lives elsewhere*. (1) **`ensure_record_dataset` / `RecordSource`** -> `recordstream` (package root): the whole body was "already a `Stream`? else wrap in one", so it knew nothing but recordstream types. (2) **The prediction-output contracts + their torch builders** (`ClassificationOutput` / `DetectionOutput` / `SegmentationOutput`, `classification_output` / `segmentation_output`) -> `recordstream.outputs`: they describe the model->sink boundary, and the sink that reads them moved too. (3) **`PredictionsSink` + `ClassificationPredictionsSink`** -> `recordstream.predictions`: the sink's own justification for living here was circular ("marainer owns the contract AND the output type"), its body is record plumbing plus numpy argsort, and its "modality-neutral" claim was false — its diagnostics named `pack_id` / `iq_file` / `window_start_sample` (fixed in the move: a record is identified by ORDINAL). (4) **The class-weight arithmetic** -> `recordstream.inverse_frequency_weights` / `class_counts`: how often each class occurs is a statistic over the LABELS, not a property of a loss. **`collate_fn_with_metadata` was DELETED** — no workspace consumer called it, and git history is the archive. What did NOT move: the framework half of balancing ("does this loss take `weight=`, and how do I inject it?") is a per-backend convention and lives in the consuming runnable as an overridable method (see sonair's `accepts_class_weights` / `apply_class_weights`) — recordstream must never learn what a loss is. There are **no back-compat aliases**; a stale `from marainer.sinks import …` / `marainer.torch.outputs` import fails loudly, which is the intent.
- **The Per-Split Metric-Slot RULE Lives Here, At The TOP LEVEL (`marainer.metric_slots`, 2026-08-02):** `merge_metric_specs(shared, split)` (mappings merge by key so a same-named entry SHADOWS, sequences concatenate, incompatible shapes REPLACE, `None` on either side means "not chosen") + `union_metric_specs(shared, *splits)` for an engine that computes ONE set for several phases (`keras.Model.compile`, a `transformers.Trainer`'s `compute_metrics`) — where widening is the honest failure, because a metric computed on a split that did not ask for it is noise a reader ignores while a wired metric that silently reports nothing is a bug nobody can see. It moved UP from a consumer (`sonair/metric_slots.py`) when a SECOND task needed the identical rule on the same eight engines. **Why marainer:** it is the metrics VOCABULARY, which this package already owns — `build_metric_collection` / `scalar_metrics` (`marainer.torch`) and `write_metrics_sidecar` (`marainer.artifacts`) — and what a "metric" IS still differs per engine (a torchmetrics template mapping, a list of `keras.metrics` objects, a list of fastai function NAMES), so only the COMBINATION generalizes and it is applied to whichever vocabulary the caller uses. **It sits at the TOP LEVEL and NOT under `marainer.torch`, which is the whole point:** that subpackage requires torch, and this module imports **nothing but the standard library** precisely so the deliberately framework-free backends (JAX, MLX, Keras, any hand-written loop) can apply the rule without a torch import entering their dependency graph — several consumers AST-scan their own modules for exactly that regression. For the same reason it is NOT re-exported from the package root: the root is the TRACKING surface, and nothing here touches a tracker. Do not move it under a framework subpackage, do not add a non-stdlib import (`tests/test_metric_slots.py::test_the_module_imports_nothing_but_the_standard_library` reads the SOURCE with `ast`, so it fails wherever the mistake is made rather than only where the framework is installed), and do not let a consumer re-derive the merge inline. Pins: `tests/test_metric_slots.py`.
- **Framework-Neutral Checkpoint Policies (`marainer.checkpoints`):** `CheckpointPolicy` base + `SaveLast` / `SaveEveryEpoch(every_n_epochs)` / `SaveBest(monitor, mode, top_k)` are declarative config carriers (zero-arg `@configurable`). Each framework subpackage translates them into its native mechanism — `marainer.lightning.build_checkpoint_callbacks` → `pytorch_lightning.callbacks.ModelCheckpoint`. Checkpointing is opt-in (no policy ⇒ the framework default). Add a new policy here; translate it in the framework helper.
- **Automatic Git Provenance (`marainer.tracking.provenance`):** `log_run_context` always stamps the `git.commit` tag (`get_git_commit_hash()`, `+ "-dirty"` on uncommitted changes) and the config-script path, and uploads the transitively-included YAML tree (`liquifai.context.included_paths`) as a `config/` artifact to every tracker. `capture_log_file` uploads the active loggair output file (`loggair.get_active_config()["log_file"]`) as a `logs/` artifact at run end. Consumers get this by calling the functions, or via `TrackingCallback` (Lightning) / `keras_tracking_callback` (TF). Don't hand-roll git/config/logfile logging elsewhere.
- **System Metrics Are Framework-Free (`marainer.tracking.system`):** `enable_mlflow_system_metrics` (the process-wide MLflow enable for `mlflow.start_run` clients), `start_system_metrics_monitor` (CPU/RAM/disk), and `MpsMetricsSampler` (a plain `start()`/`stop()` Apple-Silicon GPU sampler pushing nine `system/mps_*` scalars via `MlflowClient.log_metric`; torch + mlflow lazily imported; the inlined IOKit `PerformanceStatistics` reader replaces the buggy `apple-gpu` package). The Lightning `pl.Callback` wrappers over these live in `marainer.lightning.callbacks`; a non-Lightning platform (raidar-ultralytics) calls the functions directly.
- **Random Run Names by Default (`marainer.run_names.generate_run_name`):** The single helper for a random human-friendly `adjective_noun` slug (`coolname`, offline), used as the default `Tracker.run_name` and by consumers' merged classes. Empty prefix/postfix are skipped. Use it, not a bespoke timestamp/uuid. **The task→prefix mapping is `run_prefix(task)` beside it (2026-08-02)**, so the composed call `generate_run_name(prefix=run_prefix(task))` is the ONE line a merged train/evaluate/predict class writes — it had been an identical private `_run_prefix` in EIGHT of one consumer's backends. The mapping is deliberately MANY-TO-ONE (`fit`→`train`, `predict`→`predict`, everything else→`evaluate`): `evaluate` and `test` are two entry points but one KIND of run, and a name that said `test_funny_rabbit` for one and `evaluate_funny_rabbit` for the other would split one concept across two prefixes in every tracking backend. An unrecognised verb — including one a future runnable adds — resolves to `evaluate` rather than raising, because a run name is a LABEL and refusing to produce one is never the right answer to an unfamiliar verb. The PARAMETER is a plain `str` while the RETURN is the closed `RunPrefix` Literal, and that asymmetry is the layering: the task vocabulary belongs to the runnable (it is the `@entrypoint` set), the prefix set belongs here. Pins: `tests/test_run_names.py`.
- **The Runnable Protocol Lives in recordstream, Not marainer:** `TorchRunner` (autograd marker), `ProgressReporting` (progress callback), the `entrypoint`/`runnable_entrypoints` method-annotation mechanism, the workflow combinators (`Sequence`/`Conditional`/`Switch` + predicates), and `DatasetProcessor` all moved to `recordstream.runnable` / `recordstream.workflow` / `recordstream.processing` (see recordstream AGENTS). A consumer's merged train+eval class inherits `TorchRunner`+`ProgressReporting` from recordstream and annotates its `fit`/`evaluate`/`test`/`predict` methods with `@entrypoint`. There is no `marainer.runner`/`marainer.progress`/`marainer.workflow`/`marainer.processing`.
- **No CLI — Runs Go Through `recordstream run`:** The marainer CLI + `marainer.commands` plugin group are retired. A consumer's config roots at `runnable:` with a `task:` and runs via `python -m recordstream.cli run -c config.yaml`; consumers may also ship their own per-project CLI (`sonair train`, `raidar evaluate`, …). Don't reintroduce a marainer binary.
- **Light Core Install + Extras:** `pip install marainer` = confluid/liquifai/loggair/coolname/numpy only; `import marainer` must NOT import torch or pytorch_lightning. Everything else is behind `[torch]` / `[lightning]` / `[mlflow]` / `[tensorboard]` / `[wandb]` / `[tensorflow]` / `[all]`. When adding a backend/helper that needs a heavy lib, gate it behind an extra + a lazy `require(...)`.
- **RecordStream Lineage:** Training data flows through recordstream **records** — plain dicts of typed values. Marainer neither reshapes nor re-collates them: batching (`collate_records`), its read-back (`batch_tensor` / `batch_metadata`) and dataset normalization (`ensure_record_dataset`) are all recordstream's. If you find yourself writing a collate or a batch reader here, it belongs there.

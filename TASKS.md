- [ ] **`load_lightning_checkpoint` loads ZERO weights, silently, when it recognises no shape** @high @bug — `_extract_state_dict` (`matrainer/torch/checkpoint.py:107-113`) recognises three shapes: a live `nn.Module` under `model` (Ultralytics), a `state_dict` key (Lightning), else it returns `raw` AS the state dict. An RF-DETR `.pth` is `{'model': OrderedDict, 'optimizer', 'lr_scheduler', 'epoch', 'args'}` — the `model` entry is an OrderedDict, not a Module, and there is no `state_dict` key — so the fallback hands `load_state_dict` a 5-key mapping whose keys are `model`/`optimizer`/`lr_scheduler`/`epoch`/`args`. With the default `strict=False` NOTHING matches, nothing loads, and nothing is reported: `RFDETRModel(checkpoint_path=…/checkpoint_best_total.pth)` yields a randomly-initialised model that runs happily and scores like noise. Measured 2026-08-15 on `raidar/rf-detr-nano.pth`. Two parts: (a) warn or raise when the resolved target matches ZERO keys — a load that lands nothing is never what the caller meant, and `strict=False` exists to tolerate a re-shaped HEAD, not a wholly foreign file; (b) consider recognising the `{'model': <state-dict mapping>}` shape, which is the plain-nested form several non-Lightning trainers write. Both change behaviour for existing callers, so scope first. Workaround until then: point the wrapper at the run's `last.ckpt` (RF-DETR's PTL loop writes a real Lightning checkpoint too — verified loading tensor-for-tensor), or re-save `torch.load(p)["model"]` as a plain state dict. @2026-08-15
